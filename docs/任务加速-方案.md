# 任务加速方案：把「一步一往返」压成「一次干完」 v0.1

> 状态：**方案；`cu macro` 已实现（2026-10-27），`cu do` / `cu mail` / 步数上限未做**
> 起因：用户实测「发一封邮件 15 分钟，其它任务只会更长」，问有没有优化方案。
> 一句话：**慢的不是工具，是步数**。工具本身 10–150ms，但 agent 每调一次工具都要过一次模型（6–9 秒）。
> 本方案的目标：把**任何** GUI/网页任务的墙钟时间从「十几分钟」压到「首次 1–2 分钟、之后 10 秒级」，
> 并且**不需要为每个任务写专用工具**。

---

## 1. 实测数据（先看证据）

### 1.1 三个真实 run 的时间构成

| run | 成员 | 大脑 | 时长 | 工具调用 | 每步均摊 |
| --- | --- | --- | --- | --- | --- |
| `21:53`（insufficient balance 那次） | impl | dsh | **15m22s** | **≥100**（几乎全是 `bash`） | **≈9.2s** |
| `21:53` | rev | codex-node | 10s | 0 | —（一上来就 402） |
| `10:34` | impl | codex-node | 10m38s | ≥100 | ≈6.4s |
| `10:34` | rev | opencode-acp | 14m34s | ≥100 | ≈8.7s |
| `10-22` | impl | codex-node | 9m50s | ≥100 | ≈5.9s |
| `10-22` | m3 | dsh | 10m00s（超时） | ≥100 | ≈6.0s |

> `members[].activities` 在 `orchestrator.py` 里被截到最近 100 条，所以「100」= **至少 100 步**。
> 100 步 × 7s ≈ 12 分钟 —— 与实测一致。

### 1.2 工具本身不慢

| 操作 | 实测 |
| --- | --- |
| `cu windows` | ~0ms |
| `cu tree`（6 层 9 节点） | ~148ms |
| `cu shot`（2560×1600） | ~30ms |
| `cu browser text/click/type` | 几十 ms |
| `cu http get` | 一个网络往返（本机 ~5ms，外网看对方） |

→ **工具开销可以忽略**；瓶颈在「模型往返次数 × 每次往返的延迟」。

### 1.3 时间花在哪（逐步拆）

1. **步数爆炸**：100+ 次工具调用，而不是 10 次。
   日志里那些步骤几乎全是 `bash`（`Get-CimInstance`、`Get-ChildItem Env:`、`rg`、`Read file`…）——
   agent 在**探索**：找邮箱客户端、找环境变量、翻仓库找"节点名/大脑名"。
2. **每步一次模型往返**：DeepSeek flash 单轮 3–6s，带思考（dsh 默认有 thinking）6–9s。
3. **上下文滚雪球**：每次工具输出（`tree` 可能几千 token）都进上下文 → 越到后面越慢越贵。
4. **权限等待**：`10:34` 那次 13 条、`10-22` 那次 47 条申请 —— 每一条都可能在等人。
   （`21:53` 那次是 0 条，所以**不是主因**，但同样是墙钟杀手。）
5. **阶段串行**：实现跑完才跑审查，2 成员 ≠ 2 并行。

### 1.4 那次 402 与本方案无关（单独记录）

`Insufficient Balance` / `402` 是**上游账户余额**问题（详见 `AGENTS.md` 踩坑 #59）；
那次还把「错误被当回答」误标成「完成」，已在 `0.2.78` 修掉。本方案不解决余额，只解决**步数**。

## 2. 结论：三条腿，缺一不可

| 腿 | 解决什么 | 典型收益 |
| --- | --- | --- |
| **① 批处理**（`cu do`） | 把「6–10 次往返」压成 1 次 | 步数 ÷ 3–10 |
| **② 录制回放**（`cu macro`） | 同一类任务第二次起只 1 步 | 100 步 → **1 步** |
| **③ 连接器**（`cu mail` 等） | 高频且有协议的任务完全不碰界面 | 100 步 → **1–3 步** |

配套四件（便宜且必要）：**步数上限**、**提示层收紧**、**工具输出瘦身**、**可观测**。

> **不是"一个任务一个工具"**：专用工具只给「高频 + 有稳定接口」的（邮件/日历/表格/SQL/HTTP）；
> 其余任务靠 ① 批处理 + ② 录制回放 —— **做一次、沉淀一次、之后回放**。

## 3. 行业对照（为什么这样设计）

| 路线 | 代表产品 | 做法 | 对我们的启示 |
| --- | --- | --- | --- |
| 连接器 / API | Zapier、Power Automate 连接器、Claude/OpenAI 的 MCP、Copilot Graph | 高频件走 API，不碰界面 | 做 `cu mail`，并把 `cu http` 当通用连接器 |
| 确定性流程节点 | n8n、Dify、Coze、LangGraph、Power Automate | 固定流程写成节点/DAG，只在需要判断处放 LLM | 我们已有工作流画布；下一步把「一串 cu 命令」固化成节点 |
| **RPA 录制回放** | UiPath、Power Automate Desktop | 人操作一遍 → 存成选择器+步骤 → 回放 | **`cu macro`**：我们的优势是**审计链已经记了每一步**，可以直接从轨迹生成宏 |
| 批处理动作 | OpenAI Operator 多动作批次、Anthropic Computer Use、Playwright MCP | 一次调用提交多动作；用可访问性树/DOM 而非像素 | **`cu do`** + 浏览器 CDP（已用选择器） |
| 通用 GUI 兜底 | Claude Computer Use、OpenAI Atlas、Browser Use | 真看屏幕点鼠标 | 官方也说"慢、易错、仅在没有 API 时用"—— 我们把它当**兜底**，并用步数上限关进笼子 |

**共识**：能用接口就别用界面；能用确定性代码就别让模型一步步点；GUI agent 是最后手段。

## 4. 详细设计

### 4.1 `cu do` —— 一次调用干一串（P0）

一条命令提交**有序动作序列**，进程内一次做完，只产生**一次**模型往返。

```bash
cu do --json '[
  {"op":"window", "title":"QQ邮箱"},
  {"op":"click",  "name":"写信"},
  {"op":"type",   "class_like":"EDIT", "text":"1","name":"收件人"},
  {"op":"type",   "name":"主题", "text":"你好"},
  {"op":"type",   "class_like":"EDIT", "index":2, "text":"正文…"},
  {"op":"keys",   "keys":"CTRL+ENTER"},
  {"op":"wait",   "like":"发送成功", "timeout_ms":8000}
]'
```

规则：

| 项 | 约定 |
| --- | --- |
| 顺序 | 严格按数组顺序；`window` 之后的动作默认作用于它（不用重复给 hwnd） |
| 失败策略 | 默认**遇错即停**并返回 `{ok:false, failed_step:n, done:[...]}`；`--continue-on-error` 可改 |
| 权限 | **整批按最严的一步判定**：含动作 → 走动作闸门；含危险词 → 整批拒（fail-closed） |
| 租约 | 整批**只抢一次**桌面租约（不逐步抢） |
| 审计 | 一条 `kind=cu`（`tool=do`），note 记「步数 + 每步 op/方法/ok」，**正文只哈希** |
| 输出 | 每步一行摘要（省 token），`--verbose` 才回完整结果 |
| 上限 | 单批最多 **20 步**、总超时 **60s**（防一条命令跑飞） |

**预期**：填一封邮件从 6–10 步 → **1–2 步**；整条链路 100 步 → **10–20 步**。

### 4.2 `cu macro` —— 录制回放（P0，最大解锁）

关键洞察：**我们的审计链/活动记录已经记下了每一步**，所以「录制」不需要另做屏幕录制 ——
**一次成功的运行轨迹就是宏**。

```bash
# 从某次运行里提取（agent 跑通的轨迹 → 宏）
cu macro save send-mail --from-run run_20261026-215334_e807c6
# 也可以从审计链按时间窗/actor 提取
cu macro save send-mail --from-audit --since 2h

cu macro list
cu macro show send-mail
cu macro play send-mail --set to=xxx@qq.com --set subject=周报 --set body=…
cu macro rm send-mail
```

宏文件格式（`runtime/state/_cu_macros.json`）：

```jsonc
{
  "send-mail": {
    "v": 1,
    "created": "2026-10-26T22:40:00",
    "source": {"run": "run_…", "member": "m1", "steps": 37},
    "target": {"kind": "window|browser", "match": {"title_like": "QQ邮箱", "class_like": "…"}},
    "params": ["to", "subject", "body"],
    "steps": [
      {"op": "click", "name": "写信"},
      {"op": "type", "name": "收件人", "text": "{{to}}"},
      {"op": "type", "name": "主题", "text": "{{subject}}"},
      {"op": "keys", "keys": "CTRL+ENTER"}
    ]
  }
}
```

设计要点：

| 项 | 约定 |
| --- | --- |
| 提取来源 | 优先 `run.members[].activities`（含 name/kind/detail）；不够再读审计链 `source=cu` |
| 稳定性 | **不存 hwnd 数值**（会变），存 `title_like` / `class_like` / `name` / `selector`；回放时重新解析 |
| 参数化 | 提取时把 `type` 的文本标成 `{{param}}`（同一文本在多次运行里出现 → 直接当变量；否则人工/UI 改） |
| 回放失败 | 任何一步失败 → **立即停**，返回「第 n 步失败（元素找不到）→ 宏可能过期，改用探索模式」 |
| 过期处理 | 失败时给 `cu do` 的等价探索命令作为回退；UI 上把该宏标「可能过期」 |
| 权限 | 回放 = 动作（整批按 4.1 的规则判定）；宏本身**不能**存"允许危险操作" |
| 审计 | 一条 `tool=macro`，记宏名 + 参数（值只哈希）+ 每步结果 |
| 存放 | 本机 `runtime/state/_cu_macros.json`（不进仓库）；可 `export` 成 JSON 放进工作流/技能 |

**为什么不做"人手录制"**：屏幕录制/焦点监听在 Windows 上极易漏事件（自绘控件、IME、异步弹窗）；
而**审计链里的轨迹**是现成的、结构化的、已经过权限与审计的动作序列 —— 更可靠。

**预期**：同一类任务第二次起 **100 步 → 1 步**（10 秒级）。

#### 4.2.1 ✅ 实现记录（2026-10-27）

已落地：`backend/computer/macro.py` + `tools/cu.py` 的 `cu macro save/list/show/play/rm/export` + `tools/cu_macro_test.py`（47 项）。

与原文的偏差（都是有理由的）：

| 项 | 原文 | 实际 | 为什么 |
| --- | --- | --- | --- |
| 提取来源 | 优先 `run.members[].activities` | **只读审计链**（`source=cu`，可按 `ref.run` / 时间窗筛） | `activities` 只留最近 100 条、且只有工具**标题**，没有命令原文/控件定位；审计里有 `loc={...}` + `ref.run` |
| 控件定位 | 只提"名字" | 审计 note 里新增 **`loc={"n","r","a","c"}`**（名字/角色/AutomationId/类名） | 回放要能"重新解析"，只存名字对输入框（名字=内容）不稳 |
| 参数 | 人工/UI 改 | 按控件名自动命名（`to`/`subject`/`body`…）+ `p1..pN` 兜底 + `param_hints` | 少一步手工；认不出也不丢信息 |
| 危险动作 | 宏不能存"允许危险" | 存 `danger`，回放要 `--allow-danger`；**回放时按当前步骤重算** | 宏文件本机可编辑，光信存档会被绕过 |
| 过期处理 | 给等价 `cu do` 探索命令 | 给 `cu tree/find` 提示 + 列表标 `stale` | `cu do` 还没做 |
| 类型步骤 | — | 默认 `replace: true`（先全选再输入）+ 找不到时**退回只用类名**再试一次 | 输入框的 UIA 名常是它当前内容；重填不该追加 |

**实测**：真窗口「7 + 8 =」4 步 → 存宏 → 干跑预检（4 个控件都找得到）→ 回放 **~200ms**（`plays`/`lastOk` 落盘）；改参数回放输入框内容真的变；故意改坏定位 → 失败在第 1 步 + 「宏可能过期」。

### 4.3 `cu mail` —— 高频任务的专用连接器（P1）

```bash
cu mail status                       # 配置是否就绪（只回掩码）
cu mail send --to a@b.com --subject 你好 --body "…" [--attach path]
cu mail inbox --limit 5 [--unread]
```

| 项 | 约定 |
| --- | --- |
| 协议 | SMTP（`smtp.qq.com:465` SSL）/ IMAP（`imap.qq.com:993`）；QQ 邮箱需要**授权码**（不是登录密码） |
| 配置 | `runtime/state/_mail.json`（`host/port/user/pass/from`），接口 GET **只回掩码**；env 可覆盖 |
| 权限 | `send` = **动作**；且「发送」是危险词 → 需要 `trust` 或显式 `--allow-actions`（邮件发出去不可撤销） |
| 审计 | 记 `to` / `subject` 的 sha256 + 正文 len/hash，**不记正文**（与 `cu type` 口径一致） |
| 依赖 | 纯标准库 `smtplib` / `imaplib`（不需要第三方） |

**预期**：邮件任务 **100 步 → 1–3 步**（10–20 秒）。

### 4.4 步数上限（P1，把最坏情况关进笼子）

| 项 | 约定 |
| --- | --- |
| 默认 | `maxSteps = 40`（每成员），env `COCRAFT_ORCH_MAX_STEPS` / 工作流成员字段可覆盖 |
| 计数 | `session.tool.called`（不含 think） |
| 到量 | **不硬杀**：发中断 + 收尾成 `failed`，`error = "到达步数上限 40（成员权限旁可调）；已完成：…"` |
| UI | 运行详情显示 `步数 12/40`；>60 步给「该换专用工具 / 存成宏」的提示 |
| 与超时关系 | `RUN_TIMEOUT`（1800s）仍在，但步数上限更早触发 |

**预期**：最坏情况 15 分钟 → **≤4 分钟**，且用户知道"卡在哪一步"。

### 4.5 提示层收紧（P0，几乎免费）

在 `CU_CARD`（每轮注入）与工作流运行上下文里加三条：

1. **多步请用 `cu do` 一次提交**（不要一步一条命令）。
2. **成员 / 阶段 / 目录 / 节点名已在上下文里 —— 不要 grep 仓库找名字**（`21:53` 那 100 步里一半是干这个）。
3. **能用 `cu http` / `cu mail` 就别用 GUI**；GUI 是最后手段。

### 4.6 工具输出瘦身（P1）

| 工具 | 现在 | 改成 |
| --- | --- | --- |
| `cu tree` | `--depth 4 --max-nodes 300` | 默认 `--prune --depth 3 --max-nodes 120`（`--full` 才给全量） |
| `cu browser text` | limit 8000 | 默认 2000 |
| `cu windows` | limit 20 | 默认 10 |
| 所有输出 | 原样 | 硬截断 **8KB**（`--full` 关闭） |

### 4.7 可观测（P2）

运行详情新增一行：`步数 37 · 每步均摊 6.8s · 上下文 42k`；
`run` 里加 `steps` 汇总字段（`public_run` 白名单记得加 —— 踩坑 #59 的教训）。

### 4.8 阶段并行（P2，可选）

阶段级 `parallel: true`，或「审查阶段提前读计划并行审」；
收益：2 成员任务墙钟时间 ≈ 砍半。

## 7. 风险与边界

| 风险 | 说明 / 对策 |
| --- | --- |
| 宏"过期"（界面改版） | 回放失败即停 + 明确提示 + 给出探索命令回退；UI 标「可能过期」；不要静默半执行 |
| 宏里带敏感值 | 提取时把文本标成 `{{param}}`，不把密码/正文写进宏；宏存本机 `runtime/state` |
| 邮件不可撤销 | `send` 必须动作闸门 + 危险词；建议默认「先存草稿再确认」或 `--allow-actions` 显式 |
| SMTP 授权码 | 只落本机 `_mail.json`；接口只回掩码；不进仓库 / 安装包 |
| 步数上限误伤长任务 | 可调（成员字段 / env）；被截断时保留已完成输出 |
| `cu do` 一步失败后面全废 | 默认即停（fail-fast）比"半成功"安全；需要时 `--continue-on-error` |
| 批处理放大风险 | 整批按**最严一步**判定；危险词命中整批拒 |

1. **`maxSteps` 默认 40** 够不够？（长任务可以调大，但默认要能兜住"15 分钟黑洞"）

## 9. 结论

- 这次慢**不是工具的问题**，是「**一步一往返**」的结构性问题；
- 解法不是"每个任务写一个工具"，而是 **① 批处理 + ② 录制回放 + ③ 高频连接器**，
  再加上 **步数上限 / 提示收紧 / 输出瘦身 / 可观测** 四件配套；
- 做完后：**邮件 15 分钟 → 10–20 秒**；一般 GUI 任务 **首次 1–2 分钟、之后 10 秒级**，且**最坏有界**。
