## 一、核心竞争力

### 1.1 真正的护城河

| 能力 | 稀有度 | 判断 |
| --- | --- | --- |
| **可逆执行闭环**：破坏性操作先隔离、每轮快照、行级 diff、一键撤销（撤销"新增"前再隔离） | ★★★★★ | 市面产品多停在"问一下 / 沙箱"；"删错了能救回来"是稀缺能力 |
| **多智能体主动编排**：角色只注入本人、一条 `@a @b` 天然并行、并排对比、审查者仲裁、一键建组 | ★★★★★ | 单 agent 产品（Claude Code / Codex / Cursor）没有；框架（AutoGen/CrewAI）没有桌面治理 |
| **引擎中立**：OpenCode + 任意 ACP agent（codex / claude / opencode / dsh） | ★★★★☆ | 不被单一厂商锁死，不依赖官方桌面版 |
| **本地主权 + 治理可见化**：权限 5 档、待批、始终允许逐条撤销、活动卡、上下文余量 | ★★★★☆ | 定位清晰；审计深度仍在补 |
| **本地协作（新）**：任务制多 agent 派活，**不经过群聊 / 登录 / 云端** | ★★★★★（进行中） | 这是修复"多智能体必须登录群聊"矛盾的关键；Runner 已落地 |
| 主题 / 技能 / 安装器 / 终端 / 编码模式 / 音乐壁纸 | ★★☆☆☆ | 表能力，负责"好用"，不负责"非它不可" |

### 1.2 一句话定位

> **敢让 AI 动你电脑的多智能体协作台 —— 因为每一步都可见、可管、可撤回。**

护城河不是单点功能，而是 **「权限 → 执行 → 留底 → 对比 → 撤回 → 审计」的闭环**，
且它是**跨引擎、多智能体、本地**的。单点都容易被抄，整合成本才是壁垒。

### 1.3 与竞品的差异

| 对手类型 | 他们的强项 | cocraft 的差异 |
| --- | --- | --- |
| OpenCode / Claude Code / Codex CLI | 单 agent 做得深、生态强 | 多 agent 分工 + 对比 + 仲裁；跨引擎；可撤回 |
| Cursor / Windsurf | IDE 体验、云端能力 | 本地优先、数据不出机；治理与撤销是主角 |
| AutoGen / CrewAI / LangGraph | 编排框架灵活 | 有真实桌面、权限、审计、人在环审批 |
| 云 Agent（Devin 类） | 托管、开箱即用 | 数据不出机；用户自己掌握 agent 与 Key |

### 1.4 风险与短板

1. **可逆执行是"尽力而为"**：只保得住能识别出的目标；codex 不报路径、猜不出时只能如实说"没保住"。
2. **agent 能力不一致**：codex 不报路径、dsh 不上报上下文；不同 agent 行为差异大。
3. **单点可被平台厂商复制**：大厂补齐"多 agent + 撤销 + 审计"后，护城河会被压缩 → 必须尽早补**分发与工作流生态**。
4. **群聊依赖云端**：当前多智能体编排在群聊里，必须先登录 cocraft → **与单机定位矛盾**（本地协作 Runner 正在修）。
5. **安全叙事反噬**：若宣传成"绝对安全 / 一定可撤回"，一次救不回来就会摧毁信任。

### 1.5 竞争力评分（1–5，判断值）

| 维度 | 分数 | 说明 |
| --- | --- | --- |
| 差异化 / 北极星 | 5.0 | 定位罕见且自洽 |
| 多智能体编排 | 4.5 | 角色/并行/对比/仲裁/建组已闭环；本地化进行中 |
| 可逆执行 | 4.0 | 文件级、best-effort；还不是事务 |
| 安全与治理 | 4.0 | 铁律落地，审计与 per-agent 上限未做 |
| 引擎中立 | 4.0 | 两引擎 + 多 agent；能力差异大 |
| 本地协作 | 3.0 | Runner 已落地，UI/审批队列未完成 |
| 测试与回归 | 4.5 | 1526 断言 + 24 套；CI 已建 |
| 工程可维护性 | 3.0 | 后端干净；前端巨石、无构建 |
| 分发与更新 | 2.5 | 机制齐全，**版本没发出去**、未签名 |
| 上手 / 文档 | 2.0 | README 已更新，但缺引导/示例/诊断 |
| 生态 / 网络效应 | 1.5 | 主题/技能可装；工作流工坊未做 |
| 平台覆盖 | 1.5 | 仅 Windows x64 |

## 四、本地协作（工作台）进度与方案

### 4.1 为什么做

当前多智能体派活 / 对比 / 仲裁长在群聊上 → 必须先登录 cocraft、建群、拉成员。
这与"单机、本地、数据不出机"矛盾。

**目标**：本机编排是默认；群聊降级为**可选的多人 / 多设备协作层**。

### 4.2 第一刀（已交付，2026-10-19）

`backend/orchestrator.py` + `/orchestrate/*`：

- 任务 / 成员模型，落 `runtime/state/_orchestrator/runs/<id>.json`；
- 每个成员独立 `AcpService` + 独立会话文件（不碰面板/群聊）；
- 并发、失败隔离、取消、超时；
- **任务级权限排队**（fail-closed；破坏性永远要确认；「始终允许」写回 ACP 记忆）；
- 结果 / tokens / context / 工具活动；仲裁（抠「推荐 X」）；
- API：catalog / runs / run / pending / start / cancel / permission / arbitrate；
- 回归：`tools/orchestrator_test.py` **27 项**；真实 `opencode-acp` 冒烟 14s 完成。

### 4.3 第二刀（下一步）：工作台 UI

1. 入口：顶栏 / 工具菜单「协作（本地）」，明确「无需登录」。
2. 新建任务：任务文本 + 工作目录 + 成员（角色 / 名字 / 引擎）+ 预设一键建组。
3. 运行详情：成员列（状态 / Markdown 输出 / tokens / 活动）、取消、重跑。
4. 待批权限卡片：成员 + 命令原文 + 允许一次 / 始终允许 / 拒绝（逐条）。
5. 对比 / 逐行差异 / 仲裁（复用现有渲染）。
6. 运行历史 + 接信任面板（时间线 / 审批历史 / 审计导出）。
7. 群聊入口标注「在线协作（需要 cocraft 账号）」。

### 4.4 已知限制

- 文件改动目前只能按**任务**统计（并发成员共享工作区）；真正的"每人改了哪些文件"需要 worktree / 独立目录。
- 表单（elicitation）第一刀自动拒绝；权限是完整排队的。
- agent 侧会话暂不自动清理（opencode-acp 会在共享库留一条会话）。

## 五、优先级结论

1. **本地协作工作台 UI**（修复单机定位矛盾；最高优先）。
2. **完成 P0 发布链路**：打包 → 签名 → VM → 推送 → Release。
3. **首次体验**：3 步引导 + 示例工作区 + 诊断导出。
4. **信任面板收尾**：可撤销列表 / 审批历史 / 活动时间线 / 审计导出。
5. **安全合规**：per-agent 上限、LICENSE、第三方声明。
6. **工作流工坊**（方向 4，补网络效应）。
7. 多机 / 团队 / 跨平台：等单机版站稳后再做。

> **一句话**：技术内核已经"能打"，现在缺的是**把本机编排做成默认、把版本发出去、让陌生人第一次就成功**。

### 6.2 现在最强的三件事

1. **本机多 agent 工作流**：可复用工作流 + 阶段串行（上一阶段产出进下一阶段）+ 条件/失败策略/重试 + 画布编辑 + 归档/另存 + 审计导出。
2. **治理闭环**：节点级权限（含 `trust`）+ **群聊成员 per-agent 上限（只紧不松）** + 逐条审批 + 隔离区/撤销。
3. **引擎中立 + 本地主权**：OpenCode + 任意 ACP agent，数据不出机，不依赖官方桌面版。

### 6.3 最短板（按优先级）

1. **发布链路**：`0.2.14`~`0.2.19` 未打包 / 未提交 / 未签名 / 未做 VM 干净机验证 —— 线上还是 `v0.2.13`。
2. **首次体验**：缺示例工作流、诊断导出；「陌生人第一次就成功」还没被验证。
3. **生态 / 分发**：工作流工坊（配方分发）未做，单机工具没有网络效应。
4. **工程可维护性**：前端单文件巨石（~15k 行、无构建）是长期风险。
5. **agent 能力一致性**：codex 不报路径、dsh 不上报上下文/命令 —— 自动化上限受制于适配器。

### 6.4 结论

一句话：**技术内核已经从「能打」变成「能讲完整故事」**；当前最大风险不在功能，而在
**版本没发出去 + 陌生人第一次用不起来**。下一步建议严格按：
① 打包 / 签名 / VM / 推送 → ② 示例工作流 + 诊断 → ③ 工作流工坊 推进。

| **可逆执行闭环**（隔离 → 快照 → 行级 diff → 撤销） | 稳定，`quarantine_test` 55 / `undo_turn_test` 18 | **仍是最大差异化**；best-effort 不是事务 |

| **治理可见化**（5 档 + 节点级 trust + per-agent 上限 + 审批时间线） | `agent_perm_cap_test` 19 / `perm_audit_test` 35 | 治理深度领先单 agent 产品 |
| **引擎中立 + 本地主权** | 两引擎 + 多 ACP agent | 结构化优势，不依赖平台 |
| **工程可维护性** | **本轮从"巨石"变"模块化"** | 从"能打"变成"能长期扛"；这是护城河能持续的底座 |

**结论没变**：护城河仍是 **「权限 → 执行 → 留底 → 对比 → 撤回 → 审计」的闭环**，且跨引擎、多智能体、本地。
本轮把这条闭环的**代码底座**从"单文件巨石"升级成"模块化 + 增量渲染 + 统一弹层 + 可观测"，
降低了"以后想加东西却不敢动"的风险 —— 但**它不会让护城河变宽，只会让护城河不掉**。

### 7.3 最短板（仍是这两个，未变）

1. **发布链路**：`0.2.14`~`0.2.20` 全部**未打包 / 未推送 / 未签名**；线上还停在 `v0.2.13`。
2. **首次体验**：缺示例工作流、诊断包未接（前端错误/性能数据已备好 `window.__diagnostics()`，但「诊断包」UI 未做）。
3. 次短板：生态/工作流工坊未做；agent 能力一致性受适配器限制。
