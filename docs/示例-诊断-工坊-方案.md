## 0. 一句话

- **示例工作流**：第一次打开工作台，不用自己想「该配几个 agent」，点一个示例就能跑。
- **诊断包**：出问题时一键导出「环境 + agent 状态 + 最近日志（脱敏）」，不用让用户翻目录。
- **工作流工坊**：把「一套成员/阶段/任务模板」做成 `workflow.json`，从 GitHub 一键装进本机。

> ⚠ 文中「诊断」按「导出诊断信息」理解。如果你说的是**争端/仲裁**，那属于已有的「对比 + 仲裁」，
> 不在本方案范围（请指正）。

## 1. 示例工作流（P1）

### 1.1 目标

- 空状态不再只有「＋ 新建工作流」；给出 4~5 个**能直接跑**的示例。
- 示例**不绑定具体 agent id**：按角色 + 本机可用 agent 自动分配。
- 点一下 = 创建一条真实工作流（可在画布上继续改），不是"演示模式"。

### 1.2 示例清单（内置）

| id | 名字 | 阶段 | 成员（角色） | 用途 |
| --- | --- | --- | --- | --- |
| `code-review` | 代码审查流水线 | 实现 → 审查 | 实现者、审查者 | 最常用；审查者能看到实现者产出 |
| `multi-model` | 多模型对拍 | 方案（2 人并行）→ 评审 | 实现者 ×2、审查者 | 同一任务两套方案 + 评审 |
| `bugfix` | 修 bug 闭环 | 定位 → 修复 → 测试 | 调研者、实现者、测试者 | 先查再改再验 |
| `research` | 调研 + 审查 | 调研 → 审查 | 调研者、审查者 | 先收集信息再复核 |
| `docs` | 撰写 + 校对 | 撰写 → 校对 | 实现者（写作）、审查者 | 文档/方案类任务 |

任务模板写成**可替换的通用句式**（如「请完成下面这件事，并说明改了哪些文件：」），不预设具体业务。

### 1.3 数据与接口

示例是**后端常量**（`orchestrator.WORKFLOW_EXAMPLES`），格式与工坊配方一致（见 §3.2）：

```jsonc
{
  "id": "code-review",
  "name": "代码审查流水线",
  "description": "实现 → 审查；审查者会看到实现者的产出",
  "taskTemplate": "请完成下面这件事，并说明改了哪些文件：\n\n",
  "stages": [{ "name": "实现" }, { "name": "审查" }],
  "members": [
    { "role": "implementer", "name": "impl", "stage": 1 },
    { "role": "reviewer", "name": "rev", "stage": 2 }
  ]
}
```

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/orchestrate/examples` | 示例列表（含成员数/阶段数，不含本机引擎） |
| POST | `/orchestrate/workflows/from-example` | `{id, name?}` → 生成真实工作流 |

**引擎分配**（`materialize_recipe()`）：

1. 取本机**可用** ACP agent（`status_of().available`）；
2. 成员可带 `engineHint`（id / label / provider 子串），命中优先；
3. 其余按「用得最少」轮转，避免全压在一个 agent 上；
4. 一个可用 agent 都没有 → 明确报错（`没有可用的 ACP agent`）；部分 hint 没命中 → 返回 `warnings`，不假装成功；
5. 生成后与手工新建完全同构（成员 id `m1..mN`、阶段 `s1..sN`、空布局）。

### 1.4 UI

- **空状态**：三步引导下面多一排「示例」卡（名字 / 一句说明 / 阶段 · 成员数 / 「用这个示例」）。
- **左栏**：在「工作流 ＋」旁加一个「工坊」小按钮（打开 §3 的工坊弹窗；示例也在里面）。
- 点击示例 → `POST from-example` → 刷新列表并选中 → 自动适应画布 → 底部任务输入预填 `taskTemplate`。
- 缺 agent / hint 未命中 → 顶部横幅写明差什么，不静默。

### 1.5 验收

- 全新机器（至少有 1 个可用 agent）→ 点「代码审查流水线」→ 工作流出现、2 阶段、可直接 ▶ 运行。
- 示例生成的工作流可正常改名 / 加阶段 / 改角色 / 归档 / 另存。
- 没有可用 agent 时给明确错误，不创建半成品。

## 2. 诊断包（P2）

### 2.1 目标

用户报「面板打不开 / agent 不回复 / 更新失败」时，不用让他手工翻 `runtime/`：
一键导出**一个脱敏 JSON（可选再带一份人读 MD）**，贴到 Issue 即可。

### 2.2 收集内容（只读、不含正文/密钥）

| 区块 | 内容 |
| --- | --- |
| 版本 | `ui` 版本、后端 pid/启动时间/uptime、Python/OS、是否安装版 |
| 引擎 | 当前引擎、OpenCode 上游是否可达、ACP 进程数 |
| agent | 每个 agent：id / label / provider / mode / available / missing（**不含 env**） |
| 密钥 | 只列 **env 变量名**（如 `DEEPSEEK_API_KEY`），值一律 `***` |
| 状态文件 | `runtime/state/*` 的**文件名 / 大小 / mtime**；会话数、run 数、工作流数（**不含内容**） |
| 权限 | 面板等级；群聊成员 `permLevel` + 生效值；危险模式 agent 标记 |
| 最近运行 | 最近 10 条 run 的 id/状态/成员数/时间（不含输出） |
| 日志 | `acp.log` / `watch.log` / `security.log` 各**最后 80 行**（脱敏） |
| 完整性 | 关键目录/文件是否存在（frontend、backend、agents、node、runtime） |

### 2.3 脱敏规则

- 键名匹配 `key|token|secret|password|cookie|authorization` → 值替换为 `***`；
- 文本里 `sk-[A-Za-z0-9_-]{6,}` → `sk-***`；
- `XxxKey=...` / `Authorization: Bearer ...` → `***`；
- **绝不包含**：消息正文、成员输出、会话标题全文、Cookie、API Key、Token；
- 用户目录路径保留（排障需要），不替换为匿名。

### 2.4 接口与落盘

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/diagnose` | 返回摘要（不落盘），供界面显示「N 项检查」 |
| POST | `/diagnose/export` | 写 `runtime/diagnostics/diag-<ts>.json`（+ `diag-<ts>.md`），回 `{path, bytes}` |

### 2.5 UI

- 设置右侧抽屉新增「**诊断**」一行：`导出诊断包` + 最近一次路径 + `打开目录`。
- 导出成功 → 横幅「已导出 …（不含密钥/正文）」；失败 → 明确原因。
- （可选）错误横幅上加「导出诊断」快捷入口；首版不做。

### 2.6 验收

- 导出文件里**搜不到任何真实 Key / Token / Cookie / 消息正文**；
- 换一台机器打开 JSON 能看懂：版本、agent 状态、日志末尾；
- 日志缺失/文件损坏时**不崩**，对应项写 `缺失`；
- 导出失败（磁盘满/权限）给明确错误。

## 3. 工作流工坊（P3）

### 3.1 目标

让「一套工作流」可以像主题/技能一样从 GitHub 安装：
**内置示例离线可用；远程仓库一行链接拉取；安装后就是普通工作流**（可改、可跑、可删）。

### 3.2 配方格式（`workflow.json`）

```jsonc
{
  "schema": 1,
  "id": "code-review",
  "name": "代码审查流水线",
  "description": "实现 → 审查；审查者会看到实现者的产出",
  "author": "huaian307",
  "taskTemplate": "请完成下面这件事，并说明改了哪些文件：\n\n",
  "stages": [
    { "name": "实现", "when": "always", "onFail": "stop", "retries": 0 },
    { "name": "审查", "when": "always", "onFail": "stop", "retries": 0 }
  ],
  "members": [
    { "role": "implementer", "name": "impl", "stage": 1, "engineHint": "" },
    { "role": "reviewer",    "name": "rev",  "stage": 2, "engineHint": "" }
  ]
}
```

- `engineHint` 可留空；也可写 `codex` / `claude` / `opencode`（按 id/label/provider 子串匹配）。
- 不含任何密钥、脚本、命令；只有配置。

### 3.3 来源与拉取

| 来源 | 行为 |
| --- | --- |
| 空 | 只列**内置示例**（离线） |
| `owner/repo` 或 GitHub 链接 | 先找 `catalog.json`；没有就扫 `workflows/**/workflow.json`（上限 30 个） |
| 直链 `.json` | 单个配方，或 `{"workflows":[...]}` catalog（内含完整配方） |

- 网络层**复用** `backend/skills_install.py` 的 GitHub tree API + 代理并行（`ghfast.top` 等），
  不新造一套；单文件大小上限沿用（几 MB）。
- 只读 JSON、只写盘；**不执行任何脚本**（与主题/技能工坊同一红线）。

### 3.4 安装流程

1. 校验配方：阶段 1~8、成员 1~8、角色归一、字符串截断（name 40 / task 2000）、非法值拒绝；
2. 引擎映射同 §1.3（hint 优先 + 最少使用轮转）；没命中给 `warnings`；
3. `save_workflow()` 落盘 → 出现在正常「工作流」列表；
4. 记录来源（新增可选字段 `source` / `installedFrom`，老工作流没有也不影响）；
5. 安装后选中 + 适应画布；失败（网络/格式）明确到具体字段。

**首版不做**：配方更新/卸载（删除工作流就是卸载）、依赖安装、自动建 agent、私钥/密钥类字段。

### 3.5 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/workshop/workflows?source=` | 列表（空 = 内置示例；含 `builtin` / `source`） |
| POST | `/workshop/workflows/install` | `{source?, id?, recipe?, name?}` → 生成工作流 |
| POST | `/workshop/workflows/preview` | （可选）只校验并回显归一后的配方，不落盘 |

### 3.6 UI

- 新增弹窗 `#wf-workshop`（复用 `.wp` 外壳）：
  - 顶部：来源输入框 + 「拉取」；空 = 内置示例；
  - 列表：名字 / 说明 / 阶段·成员 / 来源小标 / 「安装」；
  - 底部：格式说明 + 「示例仓库格式」链接（文档）。
- 入口：左栏「工作流」标题旁「工坊」；空状态「从示例开始」也打开它。
- 安装成功 → 关闭弹窗、刷新工作流列表、选中新工作流、横幅提示（warnings 一并显示）。

### 3.7 验收

- 无网络 → 内置示例仍可安装；
- 粘一个含 `workflows/*/workflow.json` 的 GitHub 仓库 → 能列出并安装；
- 非法配方（0 阶段 / 9 成员 / 缺角色字段 / 超大字符串）→ 拒绝并说明；
- 安装出来的工作流与手工建的一致：可跑、可改、可归档、可删。

## 6. 风险与非目标

| 风险 | 对策 |
| --- | --- |
| 示例把成员全压在一个 agent 上 | 最少使用轮转 + hint 优先；安装后可在画布改 |
| 工坊拉到恶意/超大 JSON | 只读 JSON、只校验配置、大小/数量上限、绝不执行 |
| 诊断包泄露密钥 | 白名单字段 + 键名/文本双重脱敏；测试里断言"搜不到 sk-" |
| 远程仓库不存在/被墙 | 内置示例离线可用；远程失败给明确原因，不影响本地 |
| 示例/配方与当前版本不兼容 | `schema` 字段 + 校验失败明确说哪一项；不做静默降级 |

**非目标（首版不做）**：配方市场评分/评论、自动更新配方、工作流依赖安装、云端托管、示例生成 agent。
