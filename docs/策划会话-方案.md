# 策划会话（Planner Session）方案 · 用一个会话管一条工作流

> 目标（用户 2026-11-09）：**用一个统一的会话**管理工作流 —— 由**专门的策划 agent** 和用户对接：
> 分析需求 → 定计划 → 给各阶段/各 agent 派活 → 汇总 → 最后把"做完了什么"反馈给用户。
> 相关：`docs/本地协作-方案.md`、`docs/工作流画布-方案.md`、`docs/工作流阶段-方案.md`、`docs/迭代方案-2026-11-06.md`。

---

## 0. 一句话

> **策划会话 = 一个"会写计划、会按计划派活、会回来汇报"的会话**；
> 它不替代工作流，而是**工作流的控制器**：计划是它的产物，工作流是计划的执行体，运行记录是它的证据。

```
用户 ⇄ 策划 agent（一个会话）
        │ 产出/修改：计划（Plan JSON）
        ▼
     工作流（stages / members / 权限 / 目录）   ← 仍然是唯一执行体
        │ ▶ 运行
        ▼
     运行（成员并行 / 隔离 / 审批 / 审计）
        │ 汇总
        ▼
     完成报告（回到同一个会话）
```

**三件事分开**：会话负责"说清楚"，计划负责"定结构"，工作流负责"真执行"。不要把它们揉成一个黑盒。

---

## 1. 非目标（先写死）

- ❌ 不让策划 agent 直接改代码（它只写计划、派活、读结果；改代码是成员的活）；
- ❌ 不让策划 agent 绕过权限 / 审批（破坏性操作仍然问用户）；
- ❌ 不做"全自动无人值守"：默认每一步计划变更与最终应用都要人点头；
- ❌ 不做云端计划服务（数据边界同团队版方案）。

---

## 2. 形态：第四类会话

| 会话类型 | 谁创建 | 用途 |
| --- | --- | --- |
| 单聊 | 用户 | 直接干活 |
| 群聊 AI 成员 | 群聊桥 | 群里被 @ |
| 工作流成员 | Runner | 执行阶段任务 |
| **策划会话（新）** | 用户 | **和用户对话 → 出计划 → 驱动工作流 → 汇报** |

- 存 `runtime/state/_planner_sessions.json`（或复用 `_acp_sessions.json` 但打 `kind:"planner"`）；
- 左侧列表单独分组「策划」，不混进单聊；
- 一个策划会话**可以绑定 1 条工作流**（v1）；P2 再支持"一个会话管多条"。

---

## 2.1 绑定与切换规则（一个会话 = 一个项目）

| 对象 | 能不能切 | 规则 |
| --- | --- | --- |
| **项目（cwd）** | ❌ **不能** | 会话创建时写死 `projectKey`（归一化 cwd）；它是权限 workspace、隔离根、快照 scope、审计 `ref.cwd` 的锚点 |
| **工作流**（同项目内） | ✅ 能（P2；P0 先一对一） | 一个项目可以有多条工作流；切换只是换"当前操作对象"，计划重新加载 |
| **策划 agent**（模型/厂商） | ✅ 能 | 走接力包 + 能力复核（见 `docs/策划会话-接力方案.md`） |
| **运行** | ✅ 能 | 同一会话里可以连续跑多次，每次一条 run 记录 |
| **会话本身** | ✅ 能（开新的） | 左侧列表可随时切换；不同项目 = 不同会话 |

**为什么项目不能切**：

1. 权限判定用 `run.cwd / member 的隔离目录` 做"区内/区外"，混项目会让审批基准漂移；
2. 隔离（worktree / 影子副本）以项目为根，换项目等于换一整套工作区；
3. 快照、隔离区、审计的 `ref.cwd` 都按项目归档，混了以后"这条改动属于哪个项目"说不清；
4. 交接包里"硬约束 + 目标"是按项目写的，换项目等于目标冲突。

**想换项目只有两条路**：

- **新建策划会话**（推荐）：一句话带过来"沿用上个会话的约束/模板"（只复制 CORE，不复制聊天记录）；
- **派生到新项目**（fork）：把当前交接包改 `projectKey` 后作为新会话的第一条，明确是**新会话、新审计**，旧会话保留可追溯。

**同一 cwd 的不同 git 分支**：仍算同一个项目（`projectKey` 只归一化路径，不含分支）；分支差异由隔离 worktree 承担。

> 一句话：**项目是"案子"，工作流是"案子里的活"，agent 是"办事的人"。案子不能换，人和活可以换。**

---

## 2.2 切换 = 点另一个策划会话（不是"改绑定"）

左侧列表里每个**策划会话 = 一个项目**；点另一个会话就是切到另一个项目，**不会重绑任何东西**。

```
点会话 A（项目 D:\login） → 读 _planner/<A>/meta.json → 计划卡 / 阶段 / 运行状态
点会话 B（项目 D:\pay）   → 读 _planner/<B>/meta.json → 另一套计划与运行
```

切换时发生什么：

| 项 | 行为 |
| --- | --- |
| 计划 / 交接包 | 各自目录，互不影响（`_planner/<id>/plan.json`、`HANDOFF.md`） |
| 运行状态 | 只**订阅当前会话**的 run；其他会话的轮询暂停（省资源），但后台运行不受影响 |
| 未读 / 待回答 | 左侧会话行显示徽章（"待你回答 / 待批 / 刚跑完"），点进去才展开 |
| 正在跑 | 可以在 A 跑着的同时去 B 操作；A 的结果回来时在 A 行显示"完成" |
| 审计 | 每条记录带 `planner` + `project`，跨项目也能对上账 |

> 这就是"主控台"的正确形态：**面板是总台，左侧每个策划会话是一张案子**；
> 不需要"把会话切到另一个项目"——那会把两本案子的证据混在一起。

## 3. 数据模型

### 3.1 计划 `Plan`（策划 agent 的产物，结构化，可校验）

```jsonc
{
  "version": 3,
  "goal": "给登录模块加短信验证码，并通过现有测试",
  "constraints": ["不要改登录接口的签名", "必须跑 npm test"],
  "assumptions": ["已有阿里云短信 Key"],
  "acceptance": ["npm test 全绿", "新增单测覆盖验证码分支"],
  "stages": [
    { "id": "s1", "name": "调研", "when": "always", "onFail": "stop",
      "members": [{ "name": "调研", "role": "researcher", "engine": "opencode-acp", "permLevel": "read" }],
      "deliverable": "方案 + 需要改的文件清单" },
    { "id": "s2", "name": "实现", "when": "onSuccess", "onFail": "stop", "retries": 1,
      "members": [
        { "name": "后端", "role": "implementer", "engine": "codex-node", "permLevel": "trust" },
        { "name": "前端", "role": "implementer", "engine": "claude-node", "permLevel": "trust" }
      ],
      "deliverable": "代码改动" },
    { "id": "s3", "name": "审查+测试", "when": "onSuccess", "onFail": "stop",
      "members": [{ "name": "审查", "role": "reviewer", "engine": "opencode-acp", "permLevel": "read" },
                  { "name": "测试", "role": "tester", "engine": "dsh", "permLevel": "exec" }],
      "deliverable": "结论：推荐/拒绝 + 测试结果" }
  ],
  "budget": { "maxMembers": 8, "maxStages": 8, "maxMinutes": 60, "maxReplans": 2 },
  "openQuestions": []
}
```

**校验规则**（后端 `planner.validate`，不通过就退回给 agent 改）：
角色合法 / 引擎在本机可用 / 阶段 id 连续 / 成员 ≤8 / 阶段 ≤8 / `when·onFail·retries` 合法 /
`permLevel` 不超过用户设置的上限 / 目标目录存在。

### 3.2 策划会话状态机

```
intake（问清需求）
  → plan（给计划，等人确认；可多轮改）
    → running（已启动，监控）
      → review（看差异/测试，决定应用）
        → done（报告）
        ↘ replan（阶段失败 → 改计划，≤maxReplans）
```

每一步都落盘：`{phase, planVersion, runId, approvals[]}`，面板重启可恢复。

## 4. 策划 agent 怎么"动手"（关键设计）

ACP 协议没有"客户端自定义工具"，所以沿用 **cu 那套**：命令进 PATH + prompt 讲一句 + 后端闸门。

### 4.1 一个受控 CLI：`cocraft-planner`

| 命令 | 作用 | 只读/动作 |
| --- | --- | --- |
| `planner plan get` | 读当前计划（JSON） | 只读 |
| `planner plan set --file plan.json` | 提交新计划（后端校验） | 动作（需确认，见 4.3） |
| `planner run start` | 按当前计划启动运行 | **动作** |
| `planner run status [--wait]` | 看进度 / 等结束 | 只读 |
| `planner run cancel` | 取消 | 动作 |
| `planner run report` | 生成完成报告（Markdown） | 只读 |
| `planner ask --file q.json` | 向用户提问（表单） | 只读（人回答） |
| `planner apply --member m2` | **请求**把某成员改动应用回主目录 | **动作（必须人确认）** |

- 环境变量带 **每会话令牌**（`COCRAFT_PLANNER_TOKEN`），只能操作**绑定到该会话**的工作流；
- 令牌写在子进程 env，**不进审计正文**；调用一律入链 `kind=plan`；
- 没有 `shell` 权限也能用（它只调我们的 HTTP 接口，`127.0.0.1`）。

### 4.2 为什么不直接让它调 `/orchestrate/*`

- HTTP 接口没有鉴权（本机），任何有 shell 的 agent 都能调 → 令牌把范围**限制到一条工作流**；
- 令牌能撤销（关会话即失效），比"给 agent 全量接口"安全。

### 4.3 计划变更要人确认（默认）

`planner plan set` 默认**不直接生效**，而是：
1. 后端校验 → 生成 **plan diff**（成员/阶段/权限/预算的变化）；
2. 面板在会话里弹「计划有变更」卡片（新增 2 人 / s2 权限从 read 提到 trust / 预算 +20 分钟）；
3. 用户点「应用」→ 才写工作流。

> 可在设置里开「信任模式：计划自动应用」（仅限非破坏性字段：名字/阶段描述/任务文本；权限与预算永远要确认）。

## 5. 交互：一个会话里跑完全程

| 阶段 | 会话里看到什么 |
| --- | --- |
| 需求 | 策划 agent 提问（表单卡片：目标 / 目录 / 验收 / 约束 / 预算） |
| 计划 | **计划卡**：目标、阶段时间线、成员表（角色/引擎/权限）、验收、风险、开放问题；按钮「改一下」「开始执行」 |
| 执行 | **运行卡**：阶段 x/y、当前成员、待批权限（可在这里批）、"这轮改了 N 个文件" |
| 审查 | **差异卡**：每成员改动 + 冲突提示 + 「应用回主目录」；测试结果 |
| 完成 | **报告卡**：做了什么 / 改了哪些文件 / 跑了什么测试 / 谁批的 / 遗留风险 / 审计导出 |

计划卡与画布**双向**：会话里改计划 = 改工作流；画布上拖节点 = 计划版本 +1（在会话里显示"计划已更新"）。

## 6. 安全与审计

1. **不能绕过权限**：成员权限仍按成员 `permLevel` 走；策划 agent 只能"请求"应用改动；
2. **每一步入链**：计划变更 / 启动 / 审批结论 / 应用 / 取消，`kind=plan|run`，带 `ref.planVersion`；
3. **预算硬上限**：成员 8 / 阶段 8 / 单次 60 分钟 / 重规划 2 次 —— 超了直接拒绝，不让 agent 自己扩；
4. **计划 diff 可复核**：每次应用前留旧版（可以直接看"上一版计划"）；
5. **停止按钮永远有效**：会话里一个「取消全部」，等于 `run cancel`。

---

## 7. 失败处理

| 情况 | 谁决定 | 行为 |
| --- | --- | --- |
| 某成员失败（超时/报错） | 阶段策略 `onFail` | `stop` 停整条；`continue` 继续；`retries` 自动重试 |
| 阶段结论是"否决" | 策划 agent 提议 + 用户确认 | 进入 `replan`（≤2 次），在会话里给新旧计划 diff |
| 隔离冲突（主目录被改） | **只能用户决定** | 会话里列出冲突文件，用户选择覆盖 / 放弃 / 手动合并 |
| 额度不足 / 401 | 策划 agent 解释 + 停止 | 不重试（账户类错误换模型没用），给充值/换 Key 指引 |
| 用户中途改需求 | 策划 agent 改计划 | 若运行中：先取消，再改计划，再重跑（询问用户） |

## 8. 实施计划（P0 → P2）

| 阶段 | 内容 | 工作量（3 人） | 验收 |
| --- | --- | --- | --- |
| **P0** | `planner` 会话类型 + 计划 JSON + 校验 + `planner plan/run/status/report` CLI + 会话里的计划卡/运行卡/报告卡 | 2 周 | 一句话需求 → 出计划 → 人确认 → 跑完 → 会话里看到报告 |
| **P1** | 计划 diff 确认、失败自动重试/重规划（≤2）、待批权限在会话里处理、隔离应用 | 2~3 周 | 阶段失败后能给出"新计划"并等确认；冲突必须人决定 |
| **P2** | 一个会话管多条工作流（项目级）、模板化计划（复用上次成功计划）、团队版汇总 | 3~4 周 | 同一项目连续两次任务复用计划；团队能看到计划与报告 |

**P0 的最小闭环**（建议先做）：
`策划会话 → 计划卡 → [开始执行] → 运行卡 → 报告卡`，先不碰自动重规划。

---

## 9. 风险

1. **计划幻觉**：agent 可能编出不存在的引擎/过大预算 → **schema 校验 + 可用性检查**挡住；
2. **过度自动化**：默认每次计划变更要确认，避免"它自己决定加人/提权"；
3. **成本失控**：预算硬上限 + 报告中显示 tokens/费用；
4. **会话变成第二个真相源**：计划与工作流必须同步（同一次写入），画布改也要回写计划版本；
5. **策划 agent 与成员"串供"**：策划 agent 不能给自己批权限（令牌只允许请求，不允许批）。

---

## 10. 一句话总结

> **把"策划"从人的脑子里搬到一个会话里**：人只负责说清目标和点头，
> 策划 agent 负责把目标拆成阶段与人、按计划派活、盯着跑、最后把证据摊在你面前。
> 它不新增一套运行时 —— 它只是**工作流的一个会说话的遥控器 + 一个会写报告的书记员**。
