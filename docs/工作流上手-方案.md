# 工作流上手（多 agent onboarding）方案

> 状态：**草案（2026-10-23）**，待拍板先做哪个模板。
> 结论：**别把"多 agent"当卖点，把它变成"选个模板、5 分钟跑起来"。**
> 关联：`docs/路线图-2026Q4.md`（P0 / P2）、`docs/对外介绍.md`（官网与宣传）、`docs/商业模式-开源与团队版.md`（免费 vs 团队版）。

---

## 0. 一句话

> **cocraft —— 5 分钟搭出一套多 agent 流程，而且每一步都能撤回。**
> 别人改 3 个配置文件、开实验开关、自己拼阶段；你选模板、点几下、跑。

---

## 1. 现状：官方"建一个 agent"在变简单，"搭一套流程"仍然很难

（截至 2026-10，按各家公开文档整理；上游变化快，以官方为准）

| 工具 | 建一个子 agent | 搭一套**可复用工作流** |
| --- | --- | --- |
| **Claude Code** | 已不难：`/agents` → Create new agent（选范围 / 用途 / 工具） | 多 agent 团队要 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` + `--teammate-mode tmux`；**没有阶段 / 审查 / 预算的可视化配置** |
| **Codex** | 要改 `~/.codex/config.toml`（`[features] multi_agent = true`）→ 重启 → `/experimental`；自定义角色再写 `.codex/agents/*.toml` | 全靠配置文件；活动 UI 只在 CLI（`/subagents`） |
| **Cursor** | 后台 agent 上手不难（选 repo 就跑） | 没有"实现 → 审查 → 测试"的阶段、没有角色权限、没有可复用流程 |
| **OpenCode** | agent 配置写在 JSON 里 | 无画布、无模板、无阶段 |
| **共同** | 假设你会读文档、写配置、开实验开关 | **没有任何一家有"模板 → 一键导入 → 跑"的路径** |

**结论**：缝隙不在"能不能多 agent"，在"**怎么把团队流程搭起来**"。

---

## 2. 为什么这是我们的位置

| 我们已有 | 别人没有 / 难抄 |
| --- | --- |
| 工作流画布 + 阶段串行 + 条件/失败策略/重试 | 跨厂商（OpenCode + Codex + Claude + dsh 同一套画布） |
| 节点级权限 + 破坏性永不自动 + 隔离区 + 撤销 | **"流程"和"护栏"在同一处**，不是两套东西 |
| 从一次真实运行"存为工作流" | 真实运行 → 可复用流程（不是凭空写 YAML） |
| 本地、不登录、自带 Key | 模板文件可以直接发给同事，不经过服务器 |

⚠ **"易上手"本身会被追平**（Claude `/agents` 已在做向导）。真正的护城河是：
**跨厂商 + 可撤回/可审计 + 模板可分享**。窗口约 **6~12 个月**。

---

## 3. 设计目标

1. **5 分钟跑起来**：第一次打开就能跑一个真实流程，不需要读文档；
2. **安全默认**：模板不能默认宽权限；破坏性操作永远要确认；
3. **可分享**：工作流能导出成一个文件，别人导入即可（团队版卖"共享模板 + 策略下发"）。

---

## 4. 四层路径（先做 L0，不要先做 L1）

| 层 | 形态 | 给谁 | 成本 | DoD |
| --- | --- | --- | --- | --- |
| **L0 模板** | 3~5 个真实工作流，一键导入 | 第一次打开的人 | 1~2 天/个 | 点一下 → 画布出现成员/阶段 → 改目录 → 跑通 |
| **L1 向导** | 4 步：目标 → 建议成员 → 权限档 → 目录/任务 | 想自己配的人 | 3~5 天 | 不读文档能建出可跑的工作流 |
| **L2 画布** | 已有（拖节点 / 阶段 / 检查器） | 进阶用户 | 已完成 | — |
| **L3 分享** | 导出/导入 `.cocraft-workflow.json` | 团队/社区 | 2~3 天 | 换台机器导入后能跑 |

> 新用户不需要"配置能力"，需要"一个能跑的例子"。**模板优先于向导。**

---

## 5. 三个模板（都能直接跑）

### 5.1 实现 → 审查（默认推荐）

| 阶段 | 成员 | 角色 | 权限 | 模型档 |
| --- | --- | --- | --- | --- |
| 1 实现 | `impl` | implementer | `edit`（工作区内可写） | 默认（贵一点） |
| 2 审查 | `review` | reviewer | **`read`（只读，不改代码）** | 便宜档 |

- 条件：阶段 2 `when=onSuccess`；失败策略 `stop`；
- 阶段 2 自动带上阶段 1 的产出（已有 `_stage_digest`）；
- 默认任务：`实现下面的需求，并让审查者给出结论：{{task}}`；
- 验收：审查者必须输出「结论：通过 / 需要修改 + 具体问题」。

### 5.2 调研 → 方案 → 评审

| 阶段 | 成员 | 角色 | 权限 | 说明 |
| --- | --- | --- | --- | --- |
| 1 调研 | `research` | researcher | `read` + 联网 | 只查不改 |
| 2 方案 | `plan` | implementer | `edit`（只写文档目录） | 产出方案 md |
| 3 评审 | `review` | reviewer | `read` | 给「推荐 X」 |

- 适合：技术选型、迁移方案、外包报价前的调研。

### 5.3 修 bug → 测试 → 回归

| 阶段 | 成员 | 角色 | 权限 | 说明 |
| --- | --- | --- | --- | --- |
| 1 复现 | `repro` | tester | `read` | 写复现步骤，不改代码 |
| 2 修复 | `fix` | implementer | `edit` | 改代码 |
| 3 回归 | `test` | tester | `exec`（可跑测试） | 跑测试；失败重试 1 次 |

- 适合：接手别人的项目、修线上问题。

> 三个模板都要带一句「适合什么 / 不适合什么」，以及**成本上限**（见 §8）。

## 6. 模板文件格式

复用现有工作流结构（`_collab_workflows.json`），外面包一层元数据 + 预算：

```json
{
  "format": "cocraft-workflow",
  "version": 1,
  "id": "impl-review",
  "name": "实现 → 审查",
  "description": "一个人写、一个人审；审查者只读，结论可回退。",
  "cwdHint": "",
  "taskTemplate": "实现下面的需求，并让审查者给出结论：\n{{task}}",
  "stages": [
    { "id": "s1", "name": "实现", "when": "always", "onFail": "stop", "retries": 0 },
    { "id": "s2", "name": "审查", "when": "onSuccess", "onFail": "continue", "retries": 0 }
  ],
  "members": [
    { "id": "m1", "role": "implementer", "name": "impl", "engine": "", "permLevel": "edit", "stage": "s1" },
    { "id": "m2", "role": "reviewer", "name": "review", "engine": "", "permLevel": "read", "stage": "s2" }
  ],
  "budget": { "maxRounds": 2, "maxTokens": 200000, "onExceed": "stop" }
}
```

### 导入时自检（必须）

1. `format/version` 兼容（不兼容就明确报错，不猜）；
2. 成员 `stage` 指向存在的阶段；
3. `role` 是已知角色（不认识就归一成空，不静默建错人）；
4. `engine` 为空 = 用默认引擎；指定了就必须存在且可用；
5. `permLevel` 归一（未知 → 跟随面板）；**模板里出现 `trust` 要显式确认**；
6. `cwdHint` 不存在就让用户选目录（不偷偷用默认目录）。

## 7. 向导 4 步（L1）

```
① 你想做什么？  [ 写功能并审查 ] [ 调研出方案 ] [ 修 bug 并回归 ] [ 从空白开始 ]
② 谁来干？      按模板预填 2~3 个成员（角色 / 名字 / 引擎），可删可加
③ 权限怎么给？  实现=edit / 审查=read / 测试=exec（人话解释 + 「最严」一键）
④ 在哪跑？      选目录 + 写任务 → 预览（成员 / 阶段 / 预算）→ 运行
```

- 每步都有默认值，**一路回车也能跑**；
- 第三步必须显示人话说明（例：“`edit` = 工作区内可读写；删除/格式化仍会问你”）；
- 第四步的预览要写清：会跑几个阶段、预计轮次 / token 上限。

---

## 8. 成本护栏（官方最缺的一块）

Claude Code 的 agent teams 是"每个 teammate 一个完整会话"，token 很重；Codex 有 `max_threads/max_depth`。

| 字段 | 作用 | 实现难度 |
| --- | --- | --- |
| `maxRounds` | 每个成员最多跑几轮 | 低（`retries` 已有，扩成轮次上限） |
| `maxTokens` | 整个 run 的 token 上限，超了就停 | 中（`tokens` 已记账，需在派活前检查） |
| 成员模型档 | 贵的给实现、便宜的给审查 | 低（成员已有 model 字段） |
| 运行前预估 | “预计 N 轮 / 约 X tokens” | 低（按模板 + 目录大小粗估，标明“估算”） |

> 不做“精确计费”，只做“**别在月底才发现烧超了**”。

---

## 9. 安全默认（模板不能覆盖）

1. **破坏性操作永远要人确认**——`permLevel` 再宽也不行（现有铁律）；
2. 模板**默认不允许 `trust`**；导入带 `trust` 的模板要弹一次确认；
3. 审查者默认 `read`；要改成 `edit` 必须手动；
4. 导入不自动运行（先看画布，再点跑）；
5. 模板不能指定“隔离区关闭”之类的安全开关。

---

## 10. 分享与版本

- 导出：画布 →「导出工作流」→ `.cocraft-workflow.json`（含 `version`）；
- 导入：文件 → 自检 → 落到工作流列表（重名自动加 `-2`）；
- 版本迁移：`version` 升级时写迁移函数，**不猜**；
- 链接分享（需要托管）→ 后置；先做文件，团队用 Git/共享盘同步。

## 11. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 官方追平（Claude 向导 / Codex UI） | 卖"跨厂商 + 护栏 + 可分享"，不卖"向导"本身 |
| 模板腐烂（agent/模型/目录变了） | 导入自检 + 模板版本号 + 失败时说清"哪一项不满足" |
| 易上手掩盖风险 | 安全默认（§9）+ 模板不带 `trust` + 首次运行提示 |
| 模板太多挑花眼 | 首屏只放 3 个，其余收进「更多模板」 |
| 跨厂商差异 | 模板不写死引擎；引擎为空 = 默认；指定引擎时校验可用性 |

## 12. 验收与指标

| 指标 | 观察方式 | 及格线 |
| --- | --- | --- |
| 5 分钟完成率 | 新用户从打开到跑完第一个模板 | ≥50% |
| 模板使用率 | 新建工作流中选择模板的比例 | ≥70% |
| 首跑成功率 | 模板导入后第一次运行成功 | ≥80% |
| 成本偏差 | 实际 tokens / 预估 | ≤2x（超了要调预估） |
| 事故率 | 模板运行导致的破坏性未拦截 | **0** |

验收动作：找一个没看过文档的人，只给安装包和目录，**不提问**，看能否 10 分钟内跑完「实现 → 审查」。
