# 技能生态与跨 agent 兼容 · 方案与竞争力评估（v0.2 · 2026-10-27）

> 起因：用户问「GitHub 上的 skill 是不是只适用于特定 agent？我们能不能开发通用的」。
> 调研结论是**格式已经通用了**，所以我们真正要决定的不是"要不要做通用技能"，而是：
> **要不要为"别人的技能在我们这儿能跑"花工，以及这算不算竞争力。**
> **v0.2 补充**：现在的情况是「**有少量真实用户，但没有反馈**」→ 所以本方案派生出一件同批要做的事：
> **先把"要反馈"的通道补上**（诊断包 / 出口 / 静默失败提示，见 §8）；生态投入本身继续冻结。
>
> 相关：`docs/工作流沉淀-技能-方案.md`（把**我们自己的**跑通轨迹沉淀成技能）、
> `docs/示例-诊断-工坊-方案.md` §2（诊断包，已经写好细节、还没落地）、
> `docs/产品化与竞争力评估.md`（口径：什么算竞争力）。

## 0. 一句话

**格式层跟着标准走就行（我们已经在跟），不要造标准；兼容层只做到"装进来知道能不能跑、跑起来不越权"，
把工留给护栏层 —— 那里才是别人抄不走的。**

同批做的范围（详见 §5 / §8）：**P0 兼容层（目录补齐 + 体检 + 小标）+ A/B/C 反馈通道**（诊断包 / 出口 / 静默失败提示），
合计约 **1.5 天**；P1 工具映射与 P2 一切生态建设继续冻结。

## 1. 事实核对（2026-10-27 现查）

### 1.1 已经是事实标准

`SKILL.md` + frontmatter 这套（Agent Skills 规范）被 **Claude Code / Codex CLI / Cursor /
GitHub Copilot / Gemini CLI / Antigravity / OpenCode / Windsurf** 都读，被称 2026 年
"最接近通用标准"的东西。**差异只剩目录位置**：

| Agent | 全局 | 项目 |
| --- | --- | --- |
| Claude Code | `~/.claude/skills/` | `.claude/skills/` |
| Codex | `~/.agents/skills/`、`~/.codex/skills/` | `.agents/skills/`、`.codex/skills/` |
| Cursor | `~/.cursor/skills/`（部分版本只认项目级） | `.cursor/skills/` |
| GitHub Copilot | `~/.copilot/skills/` | `.github/skills/` |
| OpenCode | `~/.config/opencode/skills/` | `.opencode/skills/` |

### 1.2 有人实测过「同一份技能能不能跨」

agensi.io 拿**同样 10 个技能**在 6 个 agent（Claude Code / Codex CLI / Gemini CLI / Cursor /
Copilot agent / OpenClaw）上跑：**只有 2 个用了 agent 专属特性的需要小改** ——
一个是 `allowed-tools`（前置工具白名单），一个是 `context: fork`（子上下文）。
其余直接能用；Cursor 装完要重载窗口。

⇒ **约 90% 的社区技能天生通用**，不通用的是那 10%：`allowed-tools` / `context: fork` /
子 agent（`Task`） / 依赖某个 MCP / 依赖外部脚本。

### 1.3 生态现状（举例，不做背书）

- 官方：`anthropics/skills`；聚合：`VoltAgent/awesome-agent-skills`（1000+）、
  `ComposioHQ/awesome-claude-skills`
- 明确以「跨 agent / 无 agent 专属 hook」为卖点：`vercel-labs/agent-skills`、
  `addyosmani/agent-skills`、`prismatic-io/agent-skills`、`BB-Skills`
- 分发：`npx skills add <github-url>`（skills.sh 生态）
- ⚠ 聚合站给的 star 数明显不可信（见过 20 万+），**只当目录用，别当指标**。

## 2. 我们的现状（按代码，不凭印象）

| 能力 | 现状 | 缺口 |
| --- | --- | --- |
| 发现目录 | `~/.claude` · `~/.agents` · `~/.codex` · `~/.config/opencode` + 项目逐级同名（`skills.py`，规则对齐 OpenCode；越靠近 cwd 优先级越高） | **没有** `~/.cursor` · `~/.copilot` · `.github/skills` |
| 安装 | `skills_install.py` 支持 4 种来源：`owner/repo` 扫 `SKILL.md` / HTTP catalog / **Claude 插件市场** / 直链 `.md`；入口**归一成 `SKILL.md`**；可更新 / 卸载；装到跨工具共用的 `~/.agents/skills` | 装完**不告诉你它需要什么** |
| 激活（OpenCode） | 上游原生 `/api/skill` | — |
| 激活（ACP） | 协议**没有** skill → 我们自扫 + 写 `skill` 消息 + 正文进 `pendingSkills`，**下一次发言**拼在前面（`resume:true` 才立刻发） | 正文里的工具名是"那家的"，模型得自己猜 |
| 桌面工具 `cu` | **只给 ACP 子进程注入 PATH**（`process.py::_inject_cu_path`） | opencode 引擎是反代，动不了它的 PATH |
| 护栏 | 所有动作走等级判定 / 隔离区 / 审计 | ✅ 与技能无关，天然覆盖 |

## 3. 竞争力判断（先给结论：**增量很小，同意你的判断**）

按 `docs/产品化与竞争力评估.md` 的口径逐条对：

| 维度 | 竞品是否已有 | 我们的增量 | 能不能卖钱 |
| --- | --- | --- | --- |
| `SKILL.md` 格式 | **已经是标准**，所有人都在跟 | 0（跟随，不领先） | ❌ |
| 技能市场 / 安装器 | `npx skills add`、各家 `/skills add` 都有 | 我们有 4 种来源 + 跨工具目录，**持平** | ❌ |
| 跨 agent 兼容 | 社区自己在做（`vercel-labs` / `prismatic` / `BB-Skills`） | 我们多一层"体检 + 映射"，**差异不大** | ❌ |
| **技能跑起来有护栏** | **几乎没有**（原生 harness 只有工具白名单，没有隔离区 / 撤销 / 审计链） | **这是唯一真差异** | ⚠️ 间接 |

**结论（诚实版）**：

1. **格式/生态层永远不可能是我们的优势** —— 它是公共品，只要"别掉队"。
2. 唯一可能的卖点是组合句：**「别人写的技能，在我们这跑，每一步留痕、能撤、越权会被拦」**。
   注意主语是**护栏**，不是技能 —— 所以技能兼容只该做到 **"不添乱"** 级别，不该做产品卖点，
   更不该为它拉长工期。
3. 因此本方案的建议是：**P0 + 反馈通道同批做（约 1.5 天），P1 视真实需求再说，P2 明确不做。**

### 3.1 生态门槛（前提条件，2026-10-27 修正）

| 门槛 | 我们现在 | 判断 |
| --- | --- | --- |
| ① 有人用 | **有少量真实用户**（不再是 0） | 过了，但基数小 |
| ② 有人产出（为我们写技能） | **0** | 没过，且短期不可能 |
| ③ 网络效应 | 0 | 没过 |

⇒ **生态仍然不是现在该投的地方**。①刚过线，②③ 为空；而"有用户却没反馈"说明我们连
**用户在想什么**都不知道 —— 这比"生态没起来"更急，所以同批先补反馈通道（§8）。


## 4. 设计

### 4.1 分档（按性价比，不是按"能做什么"）

| 档 | 做什么 | 代价 | 建议 |
| --- | --- | --- | --- |
| **P0** | ① 目录补齐 ② 装前/列表**兼容性体检** ③ 安装报告一句 | 半天 | ✅ 做（同批） |
| **反馈通道** | A 诊断包 · B 出口 · C 静默失败提示（见 §8） | 1 天 | ✅ 做（同批，**优先于 P1**） |
| **P1** | ACP 激活时注入**工具名映射**（让 Claude 写的技能在我们这真能跑）+ 正文预算截断 | 1 天 | ⏸ 有真实抱怨再做 |
| **P2** | 把工作流/宏沉淀成技能、做技能市场、做"技能自测" | 数天 | ❌ 不做（见 §7） |

### 4.2 P0-①：目录补齐（`backend/engines/acp/skills.py`）

在现有顺序里补三家（**位置决定优先级，别打乱"越近 cwd 越优先"**）：

```
全局： ~/.claude → ~/.agents → ~/.codex → ~/.config/opencode → ~/.cursor → ~/.copilot
项目： <逐级>/.claude → .agents → .codex → .opencode → .cursor → .github
```

- `.github/skills` 是 **Copilot 的项目级路径**（GitHub 官方文档口径），只加项目级，不加全局。
- 同名 id 仍是**后注册的覆盖先注册的**（既有规则不动）。
- 只加"读"，不改任何写入路径 —— 我们的安装器仍只往 `~/.agents/skills` 等既有目标装。

### 4.3 P0-②：兼容性体检（纯函数，离线可测）

放 `backend/skills_install.py`（安装前用）+ `backend/engines/acp/skills.py`（列表用）共用一份：

```python
compat_of(frontmatter: dict, body: str, files: list[str]) -> {
  "level": "universal" | "adapted" | "limited",
  "reasons": ["命中 allowed-tools", "点名 Task 子 agent", ...],
  "needs": ["mcp:github", "subagent", "script:python", ...],
}
```

**判定信号表**（宁可少报，不要瞎报）：

| 信号 | 命中 → |
| --- | --- |
| frontmatter `allowed-tools` / `context: fork` | `limited`（原生白名单/fork 上下文，我们无法等价） |
| 正文出现 `Task(` / `subagent_type` / "子 agent" / "sub-agent" | `adapted`（拆顺序步骤可做） |
| 正文出现 `mcp__<name>` / "requires the X MCP" | `limited` + `needs: mcp:<name>` |
| 正文点名 `Bash`/`Read`/`Write`/`Edit`/`WebFetch`/`TodoWrite`（Claude 命名） | `adapted`（可映射） |
| 件里有 `scripts/` 且正文提到运行它 | `adapted` + `needs: script` |
| 以上都没有 | `universal` |

> **口径**：`universal` = 纯流程文字；`adapted` = 点名工具但能靠映射/拆步跑；
> `limited` = 需要我们没有的宿主能力（MCP / fork / 原生白名单）。
> 只做**提示**，**绝不自动改**别人的技能正文。

### 4.4 P0-③：界面（改动很小）

- 技能列表（`renderSkills`）在现有 `si-src`（来源目录）旁加一个 `si-compat` 小标：
  `通用` / `需适配` / `跑不全`，`title` 里放 reasons + needs。
- 「＋ 安装技能」的预览列表同样显示（装之前就知道）。
- 装完的横幅加一句：`已安装 3 个技能：2 个通用，1 个需要 MCP「github」（本机没有）`。

### 4.5 P1：ACP 激活时的工具映射（**可选，先不做**）

只在 ACP 引擎、只在 `injection_text()` 前面加一段固定前缀（约 200 字）：

```
【本 agent 的工具名和技能里写的不一样，请自行对应】
Bash/Shell → 你的「执行命令」工具；Read → 读文件；Write/Edit → 改文件；
WebFetch → 用 `cu http get` 或 `cu browser`（如果可用）；TodoWrite → 用你自己的计划工具；
Task/子 agent → 不支持，请拆成顺序步骤自己执行。
```

- 同时给正文加**预算截断**（比如 12000 字符，超出截断并在末尾注明"技能过长已截断，
  完整内容见 `<path>`"）—— ACP 是**每次激活注入一次**，长技能直接吃 prompt token。
- 评估口径：只有当**真实用户报「装了某个 GitHub 技能不灵」**时才做。

## 5. 实施顺序与验收（同批：P0 + 反馈通道 A/B/C）

| 步骤 | 内容 | 验收 |
| --- | --- | --- |
| 1 | 目录补齐 | 造 3 个临时目录各放一个 `SKILL.md`（`~/.cursor` / `~/.copilot` / 项目 `.github`）→ 列表里都能看到；**真实 runtime 不动** |
| 2 | `compat_of()` | 新 `tools/skills_compat_test.py`（离线，0 网络）：5 份假技能覆盖 universal / adapted / limited / mcp / script 五种判定 + 坏 frontmatter 不崩 |
| 3 | 界面小标 | 无头探针（复用 `trust_panel_test` 那套 STUB）：列表里三种标各自出现；预览列表也有 |
| **4** | **A · 诊断包**（`GET /diagnose` + `POST /diagnose/export`，细节照 `docs/示例-诊断-工坊-方案.md` §2） | 导出文件里**搜不到任何真 Key / Token / Cookie / 消息正文**；日志缺失/坏文件对应项记「缺失」不崩；导出失败给明确原因 |
| **5** | **B · 出口**：错误横幅加「导出诊断」；设置加一行「诊断与反馈」；更新后轻问一句（只打开 issue 模板，**不联网**） | 横幅上一键拿到文件路径；设置里能重复导出；全流程 0 网络请求 |
| **6** | **C · 静默失败说出来**：技能列表标 `跑不全`（缺 MCP / 要子 agent）+ 装前预览提示；`cu` 在"该 agent 拿不到"时明说 | 造一个 `allowed-tools` 的假技能 → 列表标 `跑不全` 且 `title` 写明原因 |
| 7 | 回归 | `check_features` +10~12 条；`run_suite` +1 套（51 → 52） |

预计合计：**约 1.5 天**（P0 半天 + A 半天 + B 1 小时 + C 半天，含回归）。

## 6. 风险与边界

| 风险 | 处理 |
| --- | --- |
| 别人的技能里带脚本 | 安装**只写盘、绝不执行**（现状如此，保持）；运行时那些命令仍走等级判定 / 隔离区 / 审计 |
| 有人要求"为兼容放宽权限" | **拒绝**。技能只能教它用已有工具，**拿不到新权限**；`limited` 就如实标 `跑不全` |
| 目录越加越多导致列表变慢 | 只加 3 处、每处和现有扫描同深度上限（6 层）；列表本来就是按需拉 |
| "体检"误报让人不敢装 | 宁可少报：只有**明确信号**才标；`universal` 是默认值 |
| 混淆两份方案 | 本方案只谈**别人的技能**；我们自己的技能（跑通轨迹 → `SKILL.md`）在 `docs/工作流沉淀-技能-方案.md` |
| **"没反馈"被当成"没问题"** | 现状是「有少量真实用户、无反馈」→ 默认按 **"没索取过"** 处理（§8），不按"用户满意"假设 |

## 7. 明确不做

- ❌ **不造格式、不写自己的 spec**（公共品，跟标准走即可）
- ❌ **不做技能市场/索引站**（`awesome-*` 已经太多；我们只做"装得进、看得懂"）
- ❌ **不执行安装进来的脚本**、不为兼容改权限闸门
- ❌ **不做"技能自动改写"**（把 Claude 技能自动翻译成 OpenCode 技能）—— 静默改写比报错危险
- ❌ **不做 P1**，除非有真实用户拿具体技能报错（有证据再做）
- ❌ **不做静默埋点 / 遥测**（见 §8.3）—— 会毁掉"本机、可审计"的立身之本

## 8. 反馈通道（同批做 · 2026-10-27 新增）

### 8.1 为什么要单列一节

现状不是"没人用"，而是「**有人在用、但没反馈**」。这不是"没问题"，而是**我们从没要过**：

| 原因 | 表现 | 对应动作 |
| --- | --- | --- |
| ① 没人索取 | 用户不会主动夸，也不会主动报 | **B**：更新后轻问一句 + 设置里「诊断与反馈」入口 |
| ② 报错要做功课 | "请贴日志 / 截图 / 翻 `runtime/logs`" → 直接关掉 | **A**：一键导出脱敏诊断包 |
| ③ 静默降级 | 装了 Claude 技能不灵、`cu` 在某 agent 上不可用 → 以为是自己的问题，走人 | **C**：把"跑不全"说出来 |
| ④ 反馈散在群里 | 没归集 | B 的 issue 模板 + A 的文件统一格式，便于归档 |

### 8.2 A/B/C 的边界

- **A 诊断包**：**只读、脱敏、只落本机**（`runtime/diagnostics/`）；内容与脱敏规则照
  `docs/示例-诊断-工坊-方案.md` §2.2/§2.3 —— 绝不包含消息正文、成员输出、Cookie、API Key、Token。
- **B 出口**：全部**不联网**；"轻问一句"只打开预填好的 GitHub issue 模板（用户自己按提交）。
- **C 静默失败**：只做"提示"，不做"自动修复"（自动改别人的技能正文比不提示更危险）。

### 8.3 一条底线：不做静默埋点

我们的卖点是「本机、可审计」。悄悄上报使用数据直接毁掉这个定位。
**要数据就 opt-in**：导出到本地，用户自己决定贴不贴。

### 8.4 之后可以用来回答的问题

有了诊断包，才能不靠猜地回答：用户到底用不用技能 / 卡在引擎还是组件 / 是不是在跑技能时被 `跑不全` 坑过
—— **这也是 P1（工具映射）要不要做、以及生态值不值得投的唯一依据**。

## 9. 待拍板

1. **目录补齐要不要包含 `~/.cursor` / `~/.copilot`**？（用户不用这两个 agent 的话，加了只是列表噪音）
2. **兼容性小标放在列表里，还是只在"安装预览"里**？（列表加标会让行变长）
3. **要不要顺手把 `name` / `description` 从英文翻成中文**？—— 我倾向**不做**（翻译会让 id 和正文对不上）
4. **"更新后轻问一句"要不要做**？（怕打扰；折中：只在**第一次更新成功**时问一次，可永久关掉）

## 10. 结论

**同批做：P0 兼容层（目录 + 体检 + 小标）+ A/B/C 反馈通道；不做 P1/P2。** 理由一句话：

> 技能格式是公共品，兼容层只值得做到"不添乱"；
> 我们的钱在**护栏**（谁批的、能不能退、越权会不会被拦），不在"能不能装别人的技能"。
> 而**"没反馈"比"生态没起来"更急** —— 先把通道补上，再谈生态值不值得投。
