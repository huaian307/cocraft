# 团队版架构与定位（2026-11-06）· 明文不出机，团队只同步密文

> 定位变更（用户 2026-11-06 拍板）：**从"数据不出机"改为"明文不出机"**。
> 即：本地模式仍然全程不出机；**团队版允许数据离开本机，但只以端到端密文形式**（我们和任何中转都看不到明文）。
> 相关：`docs/对外介绍.md`（对外口径）、`docs/迭代方案-2026-11-06.md`（工程优先级）。

---

## 0. 一句话

> **cocraft 团队版 = 一套"密文台账"**：
> 每台机器自己执行、自己留证；同步出去的只有**端到端加密的审计包**，密钥在客户手里；
> 我们只搬箱子，打不开箱子。

---

## 1. 数据边界（必须分三档说，别混）

| 模式 | 什么会离开本机 | 谁能看到明文 | 默认 |
| --- | --- | --- | --- |
| **本地模式（默认）** | 只有模型调用本身（你配的 Key） | 本机 / 模型厂商（按其条款） | ✅ |
| **团队·共享目录** | 签名 + 加密的审计包（放客户自己的 NAS / 网盘） | 只有装了团队密钥的成员 | 可选 |
| **团队·中继**（我们托管） | **密文** + 最少路由元数据 | **只有客户**（我们和运维都看不到） | 可选、需客户明确开启 |
| 企业自建 | 同"共享目录/中继"，走客户内网 | 客户 | 可选 |

**中继能看到什么（诚实清单）**：密文大小、上传时间、团队不透明 ID、机器不透明 ID、包的序号。
**看不到**：审计正文、命令原文、文件路径、文件名、成员姓名、运行内容。

> 缓解：包大小按 64 KB 对齐填充；机器/团队 ID 用随机不透明串（不含主机名/用户名）。

---

## 2. 四种部署形态（同一套数据格式）

| 形态 | 客户要准备什么 | 实时性 | 谁适合 |
| --- | --- | --- | --- |
| **A. 共享文件夹** | 一个 NAS / 网盘 / Windows 共享目录 | 分钟级 | 绝大多数小团队（**先做这个**） |
| **B. 团队节点** | 任意一台已装 cocraft 的机器打开「作为团队节点」 | 秒级 | 想要实时审批 / 在线状态 |
| **C. 密文中继**（我们托管或客户自建） | 一个团队码 + 网络 | 秒级 | 全远程团队；**只有密文出网** |
| **D. 企业设施** | NAS/S3（Object Lock）/ 内网 Git | 分钟级 | 有 IT、要保留策略 |

A/B/C/D **共用同一个 `bundle` 格式与验签/解密流程**，只是"箱子怎么运"不同。

## 3. 密码学设计（够用、可验证、不造轮子）

| 项 | 选择 | 说明 |
| --- | --- | --- |
| 对称加密 | **AES-256-GCM** | 每个包一个随机 nonce；AAD 绑定包头（防换头） |
| 团队密钥 | 32 字节随机，`v1/v2…` 版本化 | 由管理员生成；**从不上传** |
| 分发 | 「团队邀请包」（密码保护的文件 / 二维码） | 不走中继；管理员当面或安全渠道给 |
| 机器身份 | 每机 ed25519（复用系统 `ssh-keygen`） | 签名放在**密文内**；中继另存一份密文哈希签名防替换 |
| 轮换 | 新版本密钥 + `roster` 更新 | 被移除的成员**解不开之后**的包（之前的包已下载的仍可解 —— 如实说） |
| 中继存储 | 只存 `<team-hash>/<bundle-id>.bin` | 不存明文文件名；保留期可配 |
| 实现 | 可选组件 venv 里的 `cryptography`（AESGCM） | 没有该组件时**团队版不可用**，本地模式不受影响 |

**为什么不用"我们发一个公钥"**：那等于把解密能力也交给我们；团队密钥必须由客户自己持有。

## 4. 包格式（`bundle` v1）

```
<cipher>.bin          AES-256-GCM 密文（内容 = 下面这个 JSON）
  明文内容（只在客户机器上解出来）:
     manifest.json    机器ID / 团队ID / 时间 / agent 版本 / 运行数 / 链头链尾 / 条数
     audit.jsonl      原始审计记录（append-only + seq/prev/hash）
     runs.json        每次运行摘要（成员/阶段/结论/恢复次数）
     signature.sig    ssh-keygen -Y sign（机器密钥，覆盖 manifest+audit+runs）
  明文包头（中继可见）:
     { v, team, machine, seq, size, created, keyVer, nonce, tag }
```

控制台流程：**下载 → 本地解密 → 验签 → 验链 → 对账**（manifest 链尾 == 包内链尾；心跳是否连续）。

## 5. 威胁模型（写进合同的那几条）

1. **中继/我们**：只能看到密文 + 少量元数据；拿不到密钥就解不开。**前提是密钥真的没上传**（代码与发布物要能自证）。
2. **被移除的成员**：轮换后解不开新包；但**已经下载到本地的旧包**他仍能解 —— 无法远程擦除，必须如实告知。
3. **被攻陷的终端**：可以撒谎、可以泄露明文。加密解决"传输与存储"，**不解决"端点已被控制"**。
4. **元数据**：大小/时间/频率会泄露"有没有在干活"，用填充与不透明 ID 缓解，不能完全消除。
5. **密钥丢失**：团队密钥丢了 = 历史包永久打不开（这是 E2E 的代价）；提供"管理员备份密钥"流程（离线保存）。

## 6. 分阶段实施（3 人）

| 阶段 | 内容 | 周期 | 验收 |
| --- | --- | --- | --- |
| **P1a** | 包格式 + AES-GCM 加密 + 共享文件夹接入 + 只读台账页（本地解密） | 3 周 | 两台机器 + 一个共享目录 → 台账页能看到并验签 |
| **P1b** | 「作为团队节点」开关（LAN 推送，仍是密文） | 2 周 | 秒级审批；节点关机退回文件夹模式 |
| **P2** | 密文中继（我们托管或一键自建）+ 团队码 + 密钥轮换/吊销 | 4~6 周 | 中继磁盘上只有密文；移除成员后新包解不开 |
| **P3** | 企业：S3 Object Lock 保留、AD 组映射、离职吊销、审计报表 | 6~8 周 | 保留 N 天不可删；成员离开后旧记录可验 |

> P1a 不依赖中继 —— 先把"密文台账"跑通，再决定要不要托管中继（托管意味着我们要承担存储与合规责任）。

## 7. 对外措辞（能说 / 不能说）

| 能说 | 不能说 |
| --- | --- |
| "默认全程本地；团队版只同步**端到端密文**" | "数据绝对不出机"（团队版会出密文） |
| "**我们看不到**你的审计正文"（中继只存密文） | "零元数据"（大小/时间可见） |
| "密钥在你们手里，我们不保管" | "丢了也能恢复"（丢了就解不开） |
| "被移除成员解不开**之后**的包" | "被移除成员什么都看不到"（旧包已下载的仍在） |
| "加密保护传输与存储" | "能防住被攻陷的终端" |

## 8. 定价与分层（与数据边界绑定）

| 版本 | 数据边界 | 能力 |
| --- | --- | --- |
| Personal（免费） | 不出机 | 本机执行 / 隔离 / 回滚 / 本地审计 |
| Team Lite | 共享目录（密文） | 签名汇总 + 只读台账 + 策略文件 |
| Team | 共享目录 / 团队节点 / 密文中继 | 实时审批 / 在线状态 / 密钥轮换 / 成员吊销 |
| Enterprise | 客户自建 | WORM 保留 / AD 映射 / 支持 |

**原则不变**：安全能力不设付费墙；收费用在"团队治理与协作"。
