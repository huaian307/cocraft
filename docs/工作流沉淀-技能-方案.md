# 工作流沉淀为技能（SKILL.md + macro）· 方案与竞争力评估

> 状态：**方案，未实现**（2026-10-27）
> 缘起：用户问「这种工作流沉淀为 skill 的功能 GitHub 上有开源的吗」→ 调研；
> 接着问「做完对我们的核心竞争力提升有多大」→ 评估。
> 结论先行：**它是护城河的乘数，不是新河段**。真正的第一刀是 `cu macro`（不花模型、10 秒级），
> SKILL.md 蒸馏排第二，工坊分发排第三（见 §6 顺序）。
> 相关：`docs/任务加速-方案.md`（步数结构性问题）、`docs/产品化与竞争力评估.md`（评分表）、
> `docs/核心竞争力-增强方向.md`（方向 4 工作流工坊）。

---

## 0. 一句话

把「跑通一次的多 agent 工作流」沉淀成两种产物：

| 产物 | 谁读 | 花不花模型 | 解决什么 |
| --- | --- | --- | --- |
| **`SKILL.md`**（步骤 / 参数 / 坑 / 失败恢复） | agent | 要（但只有 1–3 步） | 「它记得怎么干」，跨任务可迁移 |
| **`macro.json`**（参数化的动作序列） | `cu macro play` | **不花** | 「同一件事第二次 10 秒」，确定性回放 |

> 我们已有的审计链里**每一步都在**（工具 / 控件 / 窗口 / 结果），所以"录制"不需要另做屏幕录制 ——
> 一次成功的轨迹就是原料。这是相对所有开源方案最实的一个起点。

## 1. 开源调研（GitHub 上有没有现成的）

**没有「跑完多 agent 工作流 → 自动写 SKILL.md + 可回放宏」的成品**；但每一段都有成熟件。

### 1.1 「跑完 → 写成 skill」

| 项目 | 做法 | 授权/状态 | 相关性 |
| --- | --- | --- | --- |
| [Acontext](https://github.com/memodb-io/Acontext) | skill 即记忆层：session → 判定任务完成/失败 → LLM 蒸馏 → 写/改 `SKILL.md`；`get_skill` 渐进披露 | Apache-2.0，**已停止维护** | ★★★★ 数据模型最贴 |
| [Trace2Skill](https://github.com/Qwen-Applications/Trace2Skill)（阿里 Qwen） | **一堆轨迹并行分析 → 各自提 patch → 分层合并成一份无冲突 skill 目录**；论文实测"单条轨迹顺序改写"明显更差 | Apache-2.0 | ★★★★★ 蒸馏方法论的正统解 |
| [EvoSkill](https://github.com/sentient-agi/EvoSkill) | 失败轨迹 → 提技能/提示变更 → 生成 → **基准集打分** → 留最好的（frontier + git 分支）；官方支持 OpenCode | Apache-2.0 | ★★★★ 需数据集 + 打分器 |
| [Hermes Agent self-evolution](https://github.com/NousResearch/hermes-agent-self-evolution) | DSPy + GEPA 用真实轨迹进化 skill / 提示 / 工具描述 | 开源 | ★★★ 持续进化参考 |
| [AWM](https://github.com/zorazrw/agent-workflow-memory) | 从历史轨迹**归纳可复用 workflow** 并按需注入 | 研究代码 | ★★★★ workflow 抽取蓝本 |
| [SkillWeaver](https://github.com/OSU-NLP-Group/SkillWeaver) | 探索后把技能**合成为可复用 API**（不是只写文档） | 研究代码 | ★★★ 「skill 必须能执行」 |
| [AutoManual](https://github.com/minghchen/automanual) | 交互中自动构建 SOP | 研究代码 | ★★ SOP 形态 |

### 1.2 「录制 → 确定性回放」（这个才真正把 15 分钟变 10 秒）

| 项目 | 做法 | 相关性 |
| --- | --- | --- |
| [workflow-use](https://github.com/browser-use/workflow-use) | 录一遍浏览器操作 → 生成带变量的确定性 workflow，**健康路径零模型调用**；失败回退 browser-use；还有「自然语言 → 跑一次 → 存成可复用 workflow」 | ★★★★★ 与 `cu macro` 几乎同构。⚠ README 自称 early development |
| [OpenAdapt](https://github.com/OpenAdaptAI/OpenAdapt) | 录桌面操作 → 编译成本地程序，**正常运行零模型调用**，带"写入校验 + 不一致就停 + 人工批准" | ★★★★★ 桌面侧最像 `cu` |
| Skyvern / Stagehand Director | 任务 → 可复用 workflow / 脚本 | ★★★ 偏网页 |

### 1.3 格式层（别自己发明）

- [agentskills.io](https://agentskills.io) 的 Agent Skills 规范 + [anthropics/skills](https://github.com/anthropics/skills)（`spec/` `template/` `skill-creator`）—— 我们的技能目录已是这个格式。
- [strands-agents/agent-sop](https://github.com/strands-agents/agent-sop)（AWS）：Markdown SOP + 参数化，可包成工具 / MCP。**多步 + 参数**比纯 `SKILL.md` 更贴，可两者并存（`SKILL.md` 挂入口 + 参数，SOP 存步骤）。
- 反向项目也有：[democra-ai/skill-to-workflow](https://github.com/democra-ai/skill-to-workflow)（skill → 多 agent workflow）。

## 2. 我们和它们的差距（好消息比坏消息多）

| 环节 | 开源现状 | cocraft 现状 |
| --- | --- | --- |
| 输入数据（轨迹） | 都要用户自己攒、格式各自定义 | ✅ 审计链（`kind=cu`：工具 / 控件 / 窗口 / 结果）+ `_orchestrator/runs/*.json` |
| 蒸馏（轨迹 → 步骤/参数/坑） | Trace2Skill 的「并行分析 + 冲突合并」是最佳实践 | ❌ 要新写（prompt + 合并流程） |
| 产物：给 agent 读 | 规范成熟 | ✅ `skills_install.py`（安装 / 更新 / 卸载 / `.cocraft.json` 来源记录） |
| 产物：确定性回放 | workflow-use / OpenAdapt 成熟 | ❌ `cu macro`（本方案 §5） |
| **权限与审计** | 基本没人做（多数 skill 只是提示词 / 脚本） | ✅ 五档权限 + 隔离区 + 撤销 + 审计链 |
| 多 agent + 阶段 + 人工审批 | 没有 | ✅ 工作流画布 |

一句话：**别人强在"蒸馏与回放"，我们强在"输入数据 + 权限审计 + 多 agent 编排"**。
缺的恰好是最容易补的一层，而且补上之后别人抄不走"另一半"。

## 3. 竞争力判断（按 `docs/产品化与竞争力评估.md` 的口径）

| 维度 | 现在 | 只做 SKILL.md | + macro + 权限审计 | 说明 |
| --- | --- | --- | --- | --- |
| 多智能体编排 | 4.8 | 4.85 | **4.9** | 从"能编排一次"到"编排一次、复用 N 次" |
| 生态 / 网络效应 | 1.5 | 1.5 | **2.0~2.5** | 只有接工作流工坊才涨 |
| 上手 / 文档 | 2.5 | 2.5 | **2.8** | 帮"第二次"，不帮"第一次" |
| 可逆执行 | 4.0 | 4.0 | **4.1** | 沉淀物也能撤销 / 进隔离区 |
| 安全与治理 | 4.5 | 4.5 | **4.6** | 只有"继承权限 + 可审"才成立 |
| 分发与更新 / 平台覆盖 | 2.5 / 1.5 | 不变 | 不变 | 与本事无关 |

综合：**+3~5%（只做文档型沉淀）／+6~9%（macro + 权限审计 + 工坊）**；成熟度公测 63% → 64~65%。
（主观估算；口径见 §4「为什么不是大提升」。）

### 3.1 为什么不是大提升

1. **能力可被抄**：Acontext / Trace2Skill / workflow-use / OpenAdapt 全开源 ——「能沉淀」本身不构成差异化。
2. **不解决当前三个短板**：版本没发出去（分发 2.5）、陌生人第一次成功（上手 2.5）、生态 1.5。
3. **它提升的是经济性不是功能性**：不改变"多 agent 有多强"，只改变"同一件事第二次要付多少钱"。

### 3.2 真正的竞争力：沉淀 × 我们独有的三件事

1. **可审计的自动化**：产物继承 `permLevel` + 每步入审计链 + 能进隔离区/撤销。
   → 对企业的说法不是"我们能自动填表"，而是**"自动填表也在治理之内"**（RPA 2.0 没人做到的那格）。
2. **成本曲线的转折**（可量化、最好讲）：第一次 15 分钟 / ≥100 步 / N 万 token；第二次 **10–20 秒 / 3–8 步 / 0 模型调用**。
3. **配方可分发**：`工作流 + 角色 + 权限建议 + macro` 打成包，复用 `themes.py` / `skills_install.py` 的网络层 ——
   这是"单机没有网络效应"的唯一现实解（成本远低于做云平台）。

## 4. 设计

### 4.1 两层产物 + 一条铁律

```text
一次成功的 run
   ├─(A) 蒸馏 → SKILL.md   参数 / 前置条件 / 危险动作 / 失败恢复 → 人审后启用
   └─(B) 提取 → macro.json 参数化动作序列 → 回放不花模型
```

**铁律**：产物**默认不启用**，人审后才进技能目录 / 宏库；产物**不能自己提权**
（危险动作每次都要显式放行，见 §4.4）。

### 4.2 数据源：审计链（不另做屏幕录制）

| 需要 | 审计里有什么 |
| --- | --- |
| 做了什么 | `action.command` = `cu click` / `cu type` / … |
| 对谁做 | `note` 里的 `loc={...}`（控件名 / 角色 / AutomationId / 类名 / 选择器） |
| 哪个窗口 | `action.title` = `click · <窗口标题>`；`note` 里的 `process=` / `class=` |
| 输入了什么 | **只有** `text len=N sha256=…` → 天然变成 `{{param}}`，**密码/正文不会进宏** |
| 哪一轮 | `ref.run` / `ref.member`（orchestrator 注入的 `COCRAFT_CU_*`） |

> 为什么不从 `run.members[].activities` 提取：那里只留最近 100 条、且只有工具**标题**，没有命令原文；
> 审计链有命令 + 定位 + 结果 + `ref.run`，是更完整的来源（**实现时的偏差，已记录**）。

### 4.3 宏格式（`runtime/state/_cu_macros.json`，不进仓库）

```jsonc
{"send-mail": {
  "v": 1, "created": "2026-10-27T09:00:00", "updated": "…",
  "source": {"kind": "audit", "since": 0, "run": "run_…", "records": 37, "actions": 6},
  "target": {"kind": "desktop", "match": {"title_like": "写邮件 - QQ邮箱",
                                          "title_words": ["QQ邮箱"], "process": "QQMail.exe"}},
  "params": ["to", "subject", "body"],
  "param_hints": {"to": {"element": "收件人", "len": 12}},
  "steps": [
    {"op": "click", "name": "写信"},
    {"op": "type", "name": "收件人", "text": "{{to}}", "replace": true},
    {"op": "keys", "keys": "CTRL+ENTER"}
  ],
  "danger": ["CTRL+ENTER"],
  "stats": {"plays": 2, "last_ok": true, "last_played": "…", "last_error": "", "last_ms": 840}
}}
```

参数名：按控件名映射（收件人→`to`、主题→`subject`、正文→`body`、密码→`password`…），认不出就 `p1..pN`
+ `param_hints` 记着它原本是哪个控件（`cu macro show` 能看到）。

### 4.4 权限与安全（不许退）

| 项 | 约定 |
| --- | --- |
| 回放分级 | `cu macro play` = **动作**（走闸门 / 黑名单 / 提权检查）；`list/show/export/save/rm` = 只读（不弹窗） |
| 危险动作 | 宏里含危险词（发送/支付/删除…）或**回车类快捷键**（`CTRL+ENTER` 之类）→ 存进 `danger`；回放必须每次显式 `--allow-danger` |
| 不提权 | 宏**不能**存"允许危险操作"；逐步仍会被 gate 拒（例如点「发送」） |
| 失败即停 | 任何一步失败立刻停，返回 `failed_step` + 「宏可能过期」+ 用 `cu tree/find` 重新探索的提示 |
| 不存 hwnd | 只存 `title_like` / `name` / `role` / `selector`，回放时重新解析（hwnd 每次都会变） |
| 审计 | 一条 `tool=macro`（名字 / 步数 / 结果 / 参数**名字**）+ 参数值走 `text=` 的哈希；每步仍各自入链 |

### 4.5 `SKILL.md` 蒸馏（P1，`cu macro` 之后）

最小实现：`GET /orchestrate/run/{id}/skill` → 读审计（`ref.run`）+ 成员输出 → 一次 LLM 蒸馏 →
落 `~/.agents/skills/<name>/`，带 `permLevel` / 危险动作 / 失败恢复 / `source` 记录（复用 `skills_install.py` 的写盘与来源记录）。

**蒸馏要按 Trace2Skill 的口径**：同一类任务至少 **3–5 条**轨迹再合并，单条轨迹就写 skill 会过拟合。

## 5. 实施顺序与验收

| 阶段 | 内容 | 验收（可自证） |
| --- | --- | --- |
| **P0（本次）** | ✅ **已完成（`cu macro`，2026-10-27）**：`save/list/show/play/rm/export` + `--dry-run` + 危险动作确认 + 失败即停 | `tools/cu_macro_test.py` **47 项**（真窗口跑 4 步 → 存宏 → 干跑 → 回放 → 改参数 → 故意破坏定位 → 失败在第 1 步 + 过期提示 + `stale`） |
| **P1** | 一次 run → `SKILL.md`（人审后启用）+ 面板入口 | 新测试：假 run 数据 → 生成内容含参数/危险动作；未确认不进技能目录 |
| **P2** | 多条同类 run 合并（并行提 patch + 冲突合并）+ 回放成功率打分 | 合并后 skill 不含互相矛盾的步骤 |
| **P3** | 接工作流工坊（配方包 = 工作流 + 角色 + 权限 + macro/skill） | 一键装一条"实现 → 审查"流水线 |

工作量：P0 **1 天**（本次已做）；P1 1–1.5 天；P2 1–2 天；P3 3–4 天。

## 6. 待拍板

1. **参数命名**：按控件名自动映射（收件人→to）够不够？要不要在面板里让用户改参数名？
2. **危险动作确认粒度**：现在按"整条宏"要 `--allow-danger`；要不要按"步"确认？
3. **宏存放**：`runtime/state/_cu_macros.json`（现在）／工作流内嵌／技能目录？
4. **`replace` 默认**：提取出的 `type` 步骤默认 `replace: true`（先全选再输入，避免追加）——够稳吗？
5. **多轨迹合并**：3 条够不够，还是 5 条？（Trace2Skill 用的是 35B/122B 规模的池子，个人场景不可能）
6. **失败回退**：宏失败后要不要自动 `cu do` 探索一把（多花一次模型），还是只给提示？

## 7. 明确不做

- ❌ 屏幕录制 / 全局键鼠钩子：Windows 上自绘控件、IME、异步弹窗极易漏事件；审计链更可靠。
- ❌ 让宏"自动修复自己"：静默改步骤比失败更危险（用户会以为还是原来那件事）。
- ❌ 把沉淀做成"云端配方市场"：与"数据不出机"冲突；先做本地库 + 工坊（GitHub）即可。
- ❌ 一上来就做 `EvoSkill` 那种"基准集进化"：个人长尾任务没有数据集和打分器，性价比极低。
